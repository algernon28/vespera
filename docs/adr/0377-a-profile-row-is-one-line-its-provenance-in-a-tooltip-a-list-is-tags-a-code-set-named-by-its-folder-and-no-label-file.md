## Context

**A profile row today** (`ProfileRow`, ADR-344 §1) draws, top to bottom: the key's descriptive name, `key-name`, which `ProfileRow.nameOf` makes by splitting the key's words; the key in small type; a description, `ProfileKey.about()` and *Read from* `ProfileKey.hint()`, wrapping; the value's control; the line *In use where the profile names none: ‹value› (‹source›)*, where `effective-values.properties` names a value beneath the profile (ADR-330 §1), the source the file's code, `shipped`, `local-file`, `command-line`, `environment`, `code` or `unknown`; the cost line, `ProfileRow.costOf`, *A change makes again:* and the stage names of `ProfileKey.cost().runs()`, then a sentence for each of its three flags; the reports, *Reports:* and a link reading each report's file name, or the name grey; then a row of the caption *Note saved with it* and a `TextField`, `<prefix><key>.provenance`, filled by `ProfileEdit.noteShown` with the provenance the file states or `set in the control panel` (ADR-343 §1); and beneath it the hint *Saved beside the value in profile.yaml so that whoever reads it later knows where the value came from. You may write how you chose the value instead.*, wrapping. The same row stands in the Profile tab (`profile-`), in `wanted` (`wanted-`) and in Seed folder (`seed-`). Its words, but for the note's, are no record's: ADR-344 §5 leaves them to the implementation.

**How the rows are drawn again.** `Cockpit.loadFiles()` builds every row of the Profile tab anew, and loads Seed folder's one row, from the file as it stands; every Save that writes calls it. The rows of `wanted` are built by `drawWanted()`, which runs only when `next-invocation.properties` is read again; `loadFiles()` draws their reports again and loads nothing else of them. So a `wanted-` row keeps what the file stated when it was drawn, and a second Save of it compares the form with that.

**`ProfileKey`** holds for each key its name in plain words, `plainName()`, a line saying what it is, `about()`, and what it is read from, `hint()`, which `TheWindowFollowsTheReadmesTableOfValuesTest` holds to the README's table of values. Of the cost's runs, no key's earliest is content census or arrangement; the five Confluence keys and `clusterPageByteCeiling` enter none (ADR-303 §9, ADR-359 §1).

**The analysis reports' titles.** Each of the twelve pages carries a title, its `<title>` and its first heading, which ADR-362 §9 copies into its JSON's `title`: *What the files turned out to be*, *Files stage 2 could not read*, *Files stage 2 read and kept*, *Confidence-score distribution*, *Document frequency of passages*, *Word counts*, *Seed/corpus mismatch*, *Copies in another language*, *How the documents grouped under each exemplar*, *Choosing the relevance cut*, *How the documents are arranged* and *Group page sizes*, some of them naming a stage or saying it in words the operator does not use.

**A list value** (`codeNameEndings`, `outOfScopeNameEndings`, `preferredLanguages`) is drawn by `listControl()` as a `TextField` holding the whole list, `<prefix><key>`, a second `TextField`, `<prefix><key>.add`, and a button `+`, `<prefix><key>.plus`, which appends the second field's text to the first. The value is the first field's text; `ProfileEdit` splits it on white space and commas (`PIECES`).

**The Code sets section** (`Cockpit.codeSetsPane()`) holds a list of entries, a folder field `code-set-folder`, a name field `code-set-name` (*A name for the deliverable (optional)*), Browse and `+`, a field `code-set-note` captioned *Note saved with the folders outside*, Save and an outcome line. A folder under the corpus root becomes an entry with the name typed, and its Save writes the entries named into `code-set-names.yaml` through `CodeSetRenames.render` (ADR-295 §7); an entry under the root given no name writes nothing. A folder outside the root goes through `CodeSetFolderChecks.refusal` and into `codeSetFolders` (ADR-334 §5), saved with the note by ADR-343 §2, through `refusalOfSave` with no digest of what was drawn, so a Save over a file another window changed since is not refused. Each load reads the file back through `CodeSetRenames.read`. `WorkingDirectoryWrite.FILES` holds `profile.yaml`, `relevance-labels.yaml` and `code-set-names.yaml`, and `WorkingDirectoryWrite.NOT_RELEVANT_FOLDERS`, `not-relevant-folders.yaml`, is the fourth file it writes.

**The jar's side of the renames.** `deliverable.CodeSetNames` reads `code-set-names.yaml` (ADR-284 §9); `Deliverable` hands its entries to `CodeCopies`, where `CodeSetFolderNames.of(sets, typed)` starts each set's folder in `code/` from its typed name or its default name, a typed name ranking first, and `CodeSetFolderNames.dormant` counts the entries naming no set of the run (ADR-296 §3.1, §6.2). `DeliverableProgress.dormantCodeSetNames` and `codeSetNamesRefused` tell `GenerationTasklet`, which records the count through `InvocationRuns` and logs a warning for a refused file; `NextAction` adds *"; D names in code-set-names.yaml name no code set of this run"* to the closing line, and `NextAction.DeliverableSummary` carries the count. `CodeCopies` writes `code.csv.part` at the tree's root, a row for each member, whose `code_set` column is the set's folder in the archive and whose `copy` column is `code/<folder in code/>/<kept path>` for a member copied; `Deliverable` moves it into place as `code.csv` after the index and the manifest. Two names of `code/` are one where `CopyNames.keysOf` gives them a key in common, as NTFS compares names. No stage reads either file, and no stage's version names `deliverable` (`StageModules`). `DeliverableProgress` takes numbers alone (ADR-274 §8).

**The label file option.** Command options holds `label-file`, *The label file for Record my answers (optional)*, with Browse; the window's plan carries it as `ControlPanelState.Plan.labelFile`, and `ChildCommand.withLabelFile` puts it, absolute, as `label`'s `<file>` (ADR-344 §4), never for `label --auto`, which refuses one (ADR-197 §6). With none, `vespera label` records the answers of the working directory's `relevance-labels.yaml`, which the Inclusions tab answers from the folders not relevant (ADR-334 §6, ADR-345). `ChildCommand.ARGUMENTS` names `label-file` as the control of `label <file>`.

**Two records not built yet.** ADR-364 §8 makes every text of the window outside a control a `SelectableText`, a `SelectableText.Line` for a text on one line and a `SelectableText.Wrapping` for one that wraps, not editable and copied by selecting it; a tooltip's text is outside that rule, and a shrunk `Line` shows its text cut at its edge with no ellipsis. ADR-362 §10 opens each analysis report natively, in a tab `analysis-report-<name>` titled by the `title` of its `<name>.json`, from the Reports section and from a key's row alike, a report whose JSON the working directory does not hold drawn grey, *not written yet*.

## Decision

### 1. A value's provenance is in its title's tooltip, and the operator writes none

**No field, line or box of the window holds a value's provenance.** The caption *Note saved with it*, its `TextField` and the hint beneath it go from every row.

**The provenance the file states for the key, where it is not blank, is the last part of the title's tooltip** (§3): after the key's own tooltip text (§4), an empty line, then *Where this value came from: ‹provenance›*, the provenance whole, as the file states it. Where the file states none for the key, or a blank one, the tooltip is the key's own text alone.

**After a Save that writes, every row of the window is loaded again from the file as it then stands**: the Profile tab's and Seed folder's, by `loadFiles()` as today, and each row of `wanted`, which `loadFiles()` now loads from the same reading of the file, keeping the rows `drawWanted()` drew. So the tooltip of every row shows what was written, whichever Save wrote it, and a second Save from `wanted` compares the form with the file as the first left it, and is not refused for a change it made itself (ADR-330 §5).

A tooltip's text is help and is not copied (ADR-364 §8). The provenance is read in the window, and copied from `profile.yaml`.

### 2. What a save writes

**A key is written by the first of two rows that matches it:**

| The value, against the file | What is written |
| --- | --- |
| as the file states | nothing: the key is not written |
| changed | the value, with **`set in the control panel`** |

The value is compared as ADR-330 §5 compares it, and a value emptied, which unsets the key, is a value changed (ADR-343 §2). So a Save of a form left alone writes nothing, and a value changed in the window never keeps the old provenance beneath it. A provenance written by hand in `profile.yaml` stays as written until its value is changed in the window.

`ProfileEdit.provenanceToSave(ProfileKey key, String value, Optional<Stated> inFile)` answers the table: empty for the first row, `FILLED_IN_PROVENANCE` for the second. Every save of a profile value calls it, the rows', the Code sets section's (§8) and the Inclusions tab's of `foldersNotWalked`. ADR-343 §4 stands for the floor `vespera label --auto` set: changed in the window, it is saved with `set in the control panel` and is the operator's from that Save on. `ProfileEdit.refusalOf`'s refusals stand (ADR-295 §4); the window, which sends no provenance but `set in the control panel`, never meets the refusal of a blank one or of the auto rule's words.

### 3. A profile row is one line

**A row's first line holds, left to right, its toggle, its title over its key, and its control.**

- **The toggle**, `<prefix><key>.more`, a `ToggleButton` in the style class `more`, drawn flat, reads *▸* while the row is closed and *▾* while it is open, its tooltip *Show what this does, what a change redoes and its reports* or *Hide them*. It is reached by Tab, and Space presses it.
- **The title**, `<prefix><key>.title`, a `SelectableText.Line` in the style class `key-name`, holds the key's title (§4). Its tooltip holds the key's own tooltip text and the provenance (§1).
- **The key**, `<prefix><key>.key`, a `SelectableText.Line` in the style class `small`, holds the key as `profile.yaml` spells it, in brackets: *(seedFolder)*. It stands just beneath the title, its left edge the title's.
- **The control** stands on the same line, to the right of the title and the key, its top within the title's line. A key edited in a section of the sidebar or in the Inclusions tab shows there its value, read-only, and its link to that place, *Edit it in its section* or *Edit it in the Inclusions tab* (ADR-344 §1, ADR-345).

**The titles of one list take one column**: the title and key of every row of the Profile tab stand in a column as wide as the widest title of that tab's rows, at most 45 % of the row's width, so that every control of the tab starts at one edge; `wanted`'s rows take a column of their own by the same rule, and Seed folder's one row its title's width. A title wider than its column is cut with "…" (§6).

**Behind the toggle**, `<prefix><key>.details`, a `VBox` beneath the first line, not visible and not managed while the row is closed, holds, top to bottom:

1. the short description, `<prefix><key>.short`, a `SelectableText.Wrapping` (§4);
2. the line of the value in use, `<prefix><key>.in-use`, a `SelectableText.Line`, where `effective-values.properties` names a value beneath the profile for the key, as ADR-330 §1 has it, and none for a key the jar names nothing beneath (§4);
3. the cost line, `<prefix><key>.cost`, a `SelectableText.Wrapping`, and its warnings beneath it, `<prefix><key>.approval`, `<prefix><key>.answers` and `<prefix><key>.new-sample`, each a `SelectableText.Wrapping` of its own and each only where the cost applies it (§4);
4. the reports, `<prefix><key>.reports`, *Reports:* and a link for each, where the key has any (§5).

**A row's open state is carried by its key**, one set of open keys for each of the Profile tab, Seed folder and `wanted`, held by `Cockpit`: a row drawn or loaded again, by a Save that writes, by Reset or by the window reading the same working directory's files again, is open where its key is in its list's set. **The sets are emptied when the working directory changes**, so that the rows drawn for another one start as follows: a row of the Profile tab or of Seed folder closed, and a row of `wanted` open, since the value it shows is the one the next start of Vespera wants answered. A key `wanted` holds for the first time starts open there.

The key in small type above the description, the description with *Read from*, and every line beneath the control that the row drew go; nothing of the row stands outside its first line and its details. Each text of a row is a `SelectableText` (ADR-364 §8); the tooltips are not. The rows of `wanted` and Seed folder are drawn by the same class.

### 4. The row's texts

**Each key's title, short description and tooltip text are data, in `src/main/resources/io/algernon/vespera/ui/profile-texts.json`**, beside `ProfileKey`: one JSON object whose names are the keys as `profile.yaml` spells them, in `ProfileKey`'s order, each value an object of three strings, `title`, `short` and `tooltip`. `ProfileKey` reads it once, through the control panel's `JsonReader` (ADR-285 §3), and answers `title()`, `shortDescription()` and `tooltip()`; `plainName()` and `about()` go, and `ProfileRow.nameOf` with them. `hint()` stays, held to the README's table as it is, and no row shows it. A file the class path does not hold, or one missing a key, fails `ProfileKey`'s first read with an `IllegalStateException` naming what is missing, which `TheProfileTextsTest` keeps from shipping.

The texts are data so that the words the operator settles change in one file, held by tests to the rules below, and in no class. The file's first texts are this section's.

**The tooltips** hold the full explanation of the value, its units and ranges, what empty, 0, 1 or a fraction does, which kinds of file it leaves alone, which report helps choose it, and the facts behind the warnings. A tooltip does not name its own key, which stands beneath the title. **It names another row by its title, in double quotes, followed by *row***, as *the "Approved grouping" row*, **and a report by its title, in double quotes, followed by *report***, as *the "Word count distribution" report* (§5), never by a file name ending `.html`; it names only the reports its own row links, or a row it names links. A report's part is named by its heading, in single quotes. The provenance is added to it by §1. The tooltips are these:

- `seedFolder`: The full path to one folder, for example D:\archive\exemplars. Put in it a handful of documents (the seed documents) you know are the kind you want kept; nothing else tells Vespera what matters to you. Vespera never changes, moves or deletes anything in this folder. If it is empty or not set, Vespera has nothing to compare your documents against, so it cannot pick which ones to keep. Documents left out are only missing from the pages, never deleted. A grouping is how Vespera puts similar documents together; if you approved one, a change here asks you to approve it again. After a change, the old relevance-labels.yaml is refused. If a seed document cannot be read because of the file itself, Vespera does not try it again; only crashes and timeouts of the reader are retried.
- `degenerateOutputConfidenceFloor`: A number from 0 to 1 (for example 0.5). When Vespera reads text out of a PDF or a scan, it gives each page of that file a quality mark from 0 to 1; the file's mark is the average over the file's own pages. Bands: below 0.5 poor, 0.5 to 0.8 fair, 0.8 to 0.9 good, 0.9 and above excellent. A file whose mark is below this number is left out: it is not in relevance-labels.yaml and not used in the pages in the Output folder. Nothing is deleted from your folders. Empty: no file is left out for its mark. 0: nothing is left out either. 1: every PDF and scan short of a perfect mark is left out. Word and plain-text files get no mark, so this number never leaves them out. No report names the files left out. The "Text quality distribution" report counts only the files kept the last time Vespera ran; to see every PDF and scan, empty this row, start Vespera again, then open it. Files whose reading failed have no mark and are not counted there; a file that failed because of the file itself is never tried again, only reader crashes and timeouts are retried.
- `degenerateOutputWordFloor`: Write a whole number, 0 or more. The panel refuses a fraction, a negative number or text and keeps the old value; if one is typed by hand into profile.yaml, Vespera treats it as no limit. Empty or 0: no file is left out for having too few words. 1 behaves like 0, because a file with no letters or digits is always left out. Words are the pieces of text between spaces; numbers and page headers and footers count. Every kind of file (Word, PDF, spreadsheet and others) uses the same number. Your seed documents are never held to it. Nothing is deleted from your folders. Files already set aside as code, logs or byte-for-byte copies stay set aside whatever this number is. The "Word count distribution" report shows, for each kind of file, how many files a limit of 2 to 10, 20, 50 or 100 words would leave out.
- `boilerplateDocumentFrequencyFloor`: When Vespera finds documents that say the same thing, it keeps only one of them; this value stops a shared letterhead or disclaimer from making documents look alike. It is a share from 0 to 1 of the documents whose text Vespera read, the number shown as N at the top of the "Repeated text across documents" report: 0.4 means 40%. Five words in a row count as repeated text when they appear in at least this share of those documents. Set too high, documents that share only a letterhead can look alike, and one of them is left out. Set too low, real shared content is ignored, so true repeats stay in. Left empty, Vespera stops before this check and writes no documentation pages. The report shows counts only, never your text, and its rows go from the lowest share at the top. If you enter the share shown on a line of the report, the passages on that line and on every line below it count as repeated text; passages on the lines above do not. Copy the value in the line's 'Share of documents' column exactly as shown. Or divide the line's 'Fewest documents' by 'N', and write the result in full or with at least as many decimal places as N has digits. Never round the result up: for passages found in 2 of 3 documents, 0.67 is above 2/3 and misses them, so write 0.666 or less. The report is written again each time Vespera reads your documents' text.
- `embeddingModel`: The name of an AI model on this computer, as known to the program that serves AI models here (set up with Vespera). Vespera comes with hf.co/Qwen/Qwen3-Embedding-8B-GGUF:Q4_K_M. This is not the writing model. Left empty, Vespera uses the model it comes with, or the one your settings name; the row's details, behind ▸, say which. If the named model is not on this computer, it is downloaded before the measuring starts (the one Vespera comes with is 4.7 GB). Each model scores closeness differently for the same documents, so after a change check the "Relevance cut-off" row and the "Translation match" row again: the same values can keep more or fewer documents. With the "Approved grouping" row set to auto, nothing waits for your approval. The new set to judge is about sixty documents; answers you already saved with Record my answers are kept. All kinds of file are affected alike. The reading of text out of your files is not redone, and a file whose reading failed because of the file itself is still not read again; only reader crashes and timeouts are retried.
- `relevanceScoreFloor`: A closeness number: how close a document is to your seed documents, as the "Comparing model" row's model measures it. Pick a value between the lowest and highest closeness shown in the "Choosing the relevance cut-off" report. The scale is not fixed: it depends on the comparing model and on how many of the closest seed documents Vespera counts for each document (that count is not a row on this tab). Empty: nothing is left out. A document below the number is only left out of the pages; your file is never deleted or moved. The cut-off is used only when every relevant / not relevant answer you saved was given under the current comparing model, or when you saved none. Otherwise it is ignored, and Vespera says so in its log and in the "Choosing the relevance cut-off" report. If you change the comparing model, mark the new documents, press Record my answers, then set this number again. Vespera may fill this number in itself from your answers, choosing the highest number that leaves out no document you marked relevant; a number you typed yourself is never overwritten. Two more reports are linked under this row: the "Group sizes" report, how many groups Vespera made, one page per group, and the "Your documents compared with your seed documents" report.
- `arrangementApproved`: Either the 12-character name that the "Grouping to approve" report shows on its own line under its heading 'What you are being asked', or the word auto. A name approves only that one grouping. If Vespera groups your documents again (for example after you change the "Relevance cut-off" row or add documents), it shows a new name and waits until you paste that new name here. auto approves every grouping without waiting for you; the report is still written each time. A name that does not match the current grouping: pages are not written until you paste the current name. A very large group can be spread over several pages (see the "Largest group page" row). Built-in value: empty, so no grouping is approved and no pages are written.
- `generationModel`: Write the model's name the way Ollama, the program that serves AI models on this computer, knows it (for example qwen3:8b). Left empty, Vespera uses the model it ships with, which the row's details, behind ▸, name. If the model is not installed, Vespera downloads it once, when it starts writing; the download is several gigabytes, and if it fails the writing stops. Vespera does not use a model that sends text off this computer, such as one whose name ends in 'cloud'. No report helps choose it. Your approval and your saved answers are kept.
- `generationContextWindow`: The number counts tokens, which are small pieces of words; Vespera counts two tokens per word. About 1,280 tokens are always kept for Vespera's instructions and for the text the model writes; the rest is for document text. So the built-in 8192 leaves about 6,900 tokens, roughly 3,450 words of document text. If you leave this empty, Vespera uses 8192. The model reads the first piece of each document's text, one document after another, starting with the documents closest to your seed documents (the documents you put in your seed folder). It skips a document whose first piece is too big to fit on its own. When the space is full, the group's remaining documents are left out, and the page says 'Written from the first N of the M documents in this group.' If no document fit, the page has no text from the model and says so, but still lists every document in the group. The panel will not save a value below 1282: that leaves room for only about one word of document text. Useful values are much higher. If profile.yaml is edited by hand to a value below 1282, Vespera stops with an error before any page is written. A larger number needs more spare memory on the computer that serves the writing model. No report helps choose it.
- `clusterPageByteCeiling`: Each group of similar documents has its own page in the Output folder. This value splits a group's page into several pages when the page would be larger than this many bytes. Pages break between documents, never inside one. The first page keeps the writing model's summary of the group, or the line saying no summary was written. A group with one document or none is never split. A page can still be larger than the limit when one document alone is. Left empty, every group stays on one page. Enter a whole number of bytes from 1 to 9223372036854775807; the panel refuses anything else and says why. If profile.yaml is edited by hand with a value that is not valid, Vespera ignores it, and the last line in the Output panel says so the next time Vespera writes the pages. The "Group page sizes" report shows how many groups there are and, for each group, the size its page would have on one page: the largest, the middle one (half are smaller), the size 95 of every 100 stay under, how many groups are larger than each of four sizes, and the ten largest (with how many documents each lists and how many pages were written for it). Once a limit is set, it also shows how many groups were split, how many pages were written in all, and how many pages are still over the limit. For a group that is split, its pictures are read again; no writing model is asked anything. When you raise the limit or empty it, a group's extra pages from before stay in its folder.
- `logTimestampShareFloor`: The value is a share from 0 to 1: 0.7 means 70% of a file's lines. A line counts when its first 64 characters hold a time stamp: a date with a time (2024-03-01 10:15, 01/03/24 10:15), a time alone (10:15:30), the form 20240301 101530, or the form 'Mar 01 10:15:30'. A date alone, such as 2024-03-01, does not count. Only text files are checked, and only those with ten or more counted lines. Blank lines are not counted, and neither are lines that carry on the line above: indented lines, or lines of an error listing that start with 'at ', 'Caused by:' or '...'. A file over 128 KB is judged only on its first 64 KB and its last 64 KB. A file left out is not used and gets no page; your files are not deleted. Set too low, documents whose lines carry clock times, such as minutes noted by the clock or exported chat transcripts, disappear from the pages without warning. Left empty, no file is left out as a log. The "What the files turned out to be" report counts the text files in each band of 10% (0-10%, 10-20%, and so on), under its heading 'How much of each text file begins with a timestamp'.
- `extractionAttempt`: A whole number. Empty or 1 means the first try; to try again, write the next number (from empty or 1, write 2). Only files left unread because the program that reads text out of your files crashed or took too long are tried again. A file that could not be read because of the file itself (for example a damaged or locked file) is never tried again, so raising the number will not help it. Files read on the new try are used like any other document. Nothing from the earlier try is deleted, and answers you saved in relevance-labels.yaml are kept. A grouping you approved must be approved again even if the groups look the same; if the "Approved grouping" row says auto, there is nothing to approve. To go back, write the earlier number (empty or 1 for the first try); going back reads no file again. Going back after approving the newer try's groups? When Vespera finishes, the last lines of the Output panel name the earlier grouping: write that name into the "Approved grouping" row. The "Files whose text could not be read" report lists those files and says which ones a new try can help.
- `codeNameEndings`: A list of name endings, each beginning with a dot, separated by spaces, with no wildcard (for example: .java .sql). Upper and lower case count the same; where two listed endings match, the longer one counts. Applies only to plain-text files (.txt, .xml, .sql, .java and the like) and to files Vespera cannot recognise (no ending or an unfamiliar one) whose beginning and end read as text. A PDF, Word or Excel file, or an image, stays a document whatever its ending. Pages made by a documentation generator, such as Javadoc, are kept as code when the generator's name or layout is written inside the page, even if their ending is not listed. Code is not grouped, and no page text is written for it. A file that changed after Vespera listed your folders is not copied to code/. If an ending is also in the "Leave out files by name ending" row, its files are left out, not kept as code. Left empty, no file is kept as code because of its name ending. A value that is not such a list is ignored, as if empty, and the last line in the Output panel says so. The "What the files turned out to be" report shows which files were kept as code and why.
- `outOfScopeNameEndings`: Endings of files you know are not documents, for example .ok .tmp. A file left out has no text read out of it, gets no page, and is not checked for duplicates; your files are never deleted. The ending is checked only for plain text files and files whose kind Vespera cannot recognise from their content. A PDF, Word or other recognised file is always kept, whatever its name ends with. Start each ending with a dot; separate endings with spaces or commas. Upper and lower case count the same. Use no asterisk, question mark, slash or backslash, and no ending made only of dots. One wrong entry makes Vespera ignore the whole list: nothing is left out by name until you fix it, and the last line in the Output panel names this setting. Empty: no file is left out by its name. In the "What the files turned out to be" report, look under 'Name endings of text files and files of no known kind' for endings to list, and under 'What the files turned out to be' for how many files the list left out. With the "Approved grouping" row set to auto, nothing waits for your approval. Answers you saved with Record my answers are kept when a new sample is picked. If you put an old list back, the pages made with it come back without being read or written again. Only files the new list lets back in have their text read out for the first time.
- `translationSimilarityFloor`: A number from 0 to 1. Near 1, two documents in different languages must say almost exactly the same thing to count as translations. Left empty, Vespera pairs documents only by their file paths: two paths are paired when they differ only in a language folder, such as en/guide/intro.docx and it/guide/intro.docx. Those path pairs are always kept, whatever this number. In the "Copies in another language" report the lines go from the lowest value to the highest, and each line lists the pairs first found at that value. A value finds the pairs on its own line and on every line after it, so pick the lowest line where neither it nor any line after it shows a wrong pair. A pair is wrong when one of its documents already has a path pair in the other language: for example it/a.docx paired with en/b.docx is wrong, because by path it/a.docx already pairs with en/a.docx. Documents in the same language are never paired by this number. Which copy of a translated document goes into the pages is decided by the "Preferred languages" row; if no copy is in a preferred language, Vespera keeps the copy whose file path comes first alphabetically; if the "Preferred languages" row is empty, every copy is kept. A change also redoes the measuring of how close each document is to your seed documents (the documents you put in your seed folder). With the "Approved grouping" row set to auto, nothing waits for your approval. Answers you already saved with Record my answers are kept.
- `preferredLanguages`: Two-letter language codes, first choice first, separated by spaces or commas, for example: it, en. Empty: every copy is kept. If one entry is not a two-letter code, Vespera ignores the whole list and keeps every copy. If no copy is in a listed language, Vespera keeps the copy whose file path comes first alphabetically. If two or more copies are in the same language, Vespera cannot pick one and keeps them all. Copies count as the same document in two ways: by the "Translation match" row, and by file paths that differ only in a language folder, such as en/guide/intro.docx and it/guide/intro.docx. Copies left out get no page; your files are not changed or deleted. The "Copies in another language" report shows the languages found and how many copies were left out.
- `configurationSettingShareFloor`: The value is a share from 0 to 1: the share of a text file's lines that are program settings, such as 'port = 8080', 'name: value' or '[section]'. 0.8 means 80%. A file counts as configuration when at least that share of its lines are settings; a lower number makes more files count. A file that counts as configuration gets no page and none of its text is used; your files are not deleted. Empty, or not a number: no file counts as configuration. Counting: blank lines and comments (#, ;, !, //) are not counted; a file needs at least ten counted lines to count by its share; for a file over 64 KB only its first and last 64 KB are read. At 1: only files made entirely of settings lines count. Above 1: no file counts by its share. At 0 or below: every text file with ten or more counted lines counts. Once a value is set, the build and logging set-up files of Maven, logback, log4j 2, .NET and Spring always count as configuration, whatever their share. Never affected: files that describe how data or a web service is laid out (XML Schema .xsd, WSDL .wsdl, OpenAPI or Swagger, JSON Schema) stay documents, unless their name ending is listed in the "Name endings that mark code" row. A configuration file inside a code folder is treated as part of that code and copied with it into code/ in the Output folder. Inside your documents folder, a code folder is the nearest folder holding a build file such as pom.xml; other code folders are listed in the "Code folders outside the documents folder" row. Answers you already saved with Record my answers are kept. The "What the files turned out to be" report shows how much of each text file is settings, under its heading 'How much of each text file is settings'.
- `deliverableLanguage`: Write en for English or it for Italian. No other language is available. If you leave it empty, the pages are in English. The language applies to the pages in the Output folder, to the browsable copy in the website folder inside it, and to the Confluence pages. The reports on this tab and the progress page stay in English whatever you pick. If you left the Output folder setting blank, the new pages go to a new folder and the old ones stay where they are. If you named an Output folder, name a new, empty one before you change the language. If you keep the old folder, Vespera rewrites the text but will not save the pages there. The rewritten text is kept, so the next time you start Vespera it is used and not written again. The next time you press Publish, the Confluence pages are replaced by the ones in the new language. Old Confluence pages with no matching page in the new language go to the Confluence trash. Your files are not read again, and the documents are not grouped again.
- `clusterResolution`: Vespera files each relevant document under the seed document it is closest to in content (seed documents are the documents you put in your seed folder). It then splits the documents under each seed document into groups by subject. This number sets how finely that split is made. Each group gets its own page in the Output folder, or several pages if it is large. Any number above 0 works; there is no upper limit and no unit. Fractions are fine, for example 0.5 or 2.5; 1 is the usual middle value. Left empty, Vespera uses its own value, 1.0 unless your settings name another. A value that is not a number above 0 (text, 0, a negative number) is ignored: Vespera uses the value it would use if the row were empty, and the progress page says so. The number changes only how documents are grouped; it does not decide which documents are kept or left out. Approval: to approve the new grouping, open the "Grouping to approve" report from the link under the "Approved grouping" row and paste the new grouping's name into that row. If that row says auto, Vespera does not wait for you and writes the pages at once, so there is nothing to approve again. The "Group sizes" report shows how many groups were made and how big each one is.
- `codeSetFolders`: One full folder path per entry, for example D:\code\billing. Add or remove these folders in the Code sets section of the sidebar. Empty: no folder outside the documents folder is read. Vespera never writes into these folders. Only the code, and the build and configuration files kept with it, is copied, unchanged, to the code/ folder inside the Output folder; other files in the folder are not copied. Documents found in these folders are treated like your other documents: their text is read, they can go into the pages, and they can be picked for you to judge as relevant or not. Vespera refuses to start if a listed folder is missing. It also refuses if a listed folder overlaps (is the same as, is inside, or contains) any of: your documents folder, your seed folder, the Output folder, the working folder (where Vespera keeps its own files), or a folder listed earlier here. With the "Approved grouping" row set to auto, nothing waits for your approval. Answers you already saved with Record my answers are kept.
- `foldersNotWalked`: A list of folders inside your documents folder. Leave it empty and every folder is read. Vespera never opens a listed folder, so the folders inside it are skipped too. Its files are not read, not compared with other documents for the same content, and never appear in a page. This is not the same as marking a folder not relevant: Vespera still reads a not-relevant folder and marks each of its files not relevant for you in relevance-labels.yaml. After a change, only files never read before have their text read out. The change applies the next time you start Vespera from the beginning; when you continue a start that was stopped, Vespera keeps the folder list it started with. With the "Approved grouping" row set to auto, nothing waits for your approval. Answers you already saved with Record my answers are kept. Code folders outside the documents folder have their own row, the "Code folders outside the documents folder" row.
- `confluenceBaseUrl`: Write the site's address starting with https://, for example https://wiki.example.com. You may add /wiki at the end, but nothing else after the site name. Only Confluence Cloud sites are supported. Left empty, Publish to Confluence cannot start; publishing only to the website (the HTML copy in the Output folder) does not need it. It works together with the Confluence space, the page or folder to publish under, and the sign-in email on this tab. The pages you published before are not moved or removed from the old site when you change it.
- `confluenceSpaceKey`: The space's short code is in its web address, after /spaces/ (for example .../wiki/spaces/DOCS/...). A Publish from this window uses the value here alone; no setting of this computer's environment changes it. Empty: Publish to Confluence refuses to start and names this setting. Publishing only the website (the HTML copy) still works. The page or folder named in the next settings (by number or by title) must be in this space. After a change, pages already in the old space stay there until you remove them yourself in Confluence. Reading, sorting and writing your documents never use this value.
- `confluenceFolderId`: Only digits: the number in the address of the Confluence page or folder, for example 123456789. The page or folder must be in the Confluence space set above. Fill in this or the "Confluence page or folder to publish under, by title" row, never both. If both or neither are filled in, Publish sends nothing and tells you to fix it. Your documents are processed the same with or without it. Publish never moves pages. After your first publish, if you point this at a different page or folder, the next Publish stops before changing anything and shows the number of the page or folder where your pages are now. To go on, put that number back, or move the page titled Vespera (and the pages under it) to the new place yourself in Confluence. Publishing only to the website copy does not use it.
- `confluenceFolderTitle`: Text, empty by default. Type the title exactly as Confluence shows it, in the Confluence space you have set. If no page in that space has this title, or more than one does, Publish stops and asks you to fill in the "Confluence page or folder to publish under, by its number" row instead. Fill in either this or the number, never both: with both filled in, or both empty, Publish sends nothing and tells you to fix it. Your pages go under one top page titled Vespera, with the others under it. Publish never moves pages: if you have already published and you point this at a different page or folder, the next Publish stops before changing anything. To go on, change this back, or in Confluence move the page titled Vespera (and the pages under it) to the new place yourself. Publishing only to the website copy does not use this setting.
- `confluenceEmail`: Text, an email address such as you@example.com. Each time you publish to Confluence from the control panel, you are asked for the API token of the same Atlassian account (a password-like key you create in your Atlassian account settings). The token is never saved. Empty: publishing to Confluence from the control panel is refused until you fill it in. Publishing only to the website (the HTML copy of the same documentation) does not need it.

### 6. A one-line text cut short shows "…"

### 9. A code set is named by its folder

**No class of the jar or the control panel reads, writes or names `code-set-names.yaml`.**

- **In the control panel**, `CodeSetRenames` goes, and `code-set-names.yaml` leaves `WorkingDirectoryWrite.FILES`, which then holds `profile.yaml` and `relevance-labels.yaml`, beside `NOT_RELEVANT_FOLDERS`, `not-relevant-folders.yaml`: the control panel writes those three files and no other, and a write naming `code-set-names.yaml` is refused as any file not among them is.
- **In the jar**, `deliverable.CodeSetNames` goes. `CodeSetFolderNames.of(sets)` starts each set's folder in `code/` from **its default name**, its folder's last element (ADR-284 §9, ADR-334 §5.5), made safe and cut as ADR-296 §3.1 has it, and tells two alike apart by the lowest member occurrence id alone: the lower keeps the name, each other takes `~` and its own. `CodeSetFolderNames.dormant`, `DeliverableProgress.dormantCodeSetNames` and `codeSetNamesRefused`, `GenerationTasklet`'s count and warning, `InvocationRuns`' record of the count, `NextAction.DeliverableSummary`'s `dormantCodeSetNames` and `NextAction`'s clause of dormant names go.

**A set whose folder in `code/` changed is told in one line.** Before it writes its own listing, `CodeCopies` reads the `code.csv` the tree's root holds from the drawing before, where there is one, and takes for each set folder of its `code_set` column the folder in `code/` of the first `copy` cell of its rows that is not empty. A drawing that fails before the listing is moved tells nothing, and the next drawing reads the same earlier listing again. A tree with no earlier `code.csv`, a set the earlier listing does not hold or holds with no copy, and a listing that cannot be read or whose header names neither column, are told nothing, and the drawing goes on. Reading the listing keys nothing, and its rows decide no name.

**How the line squares with ADR-274 §8.** ADR-274 §8 keeps every document out of the lines `pipeline` writes: no path, no file name and no document's text, `DeliverableProgress` taking numbers and enumerations alone. The line names two folders of the tree's `code/`, the tree's own names, which its index and `code.csv` already carry; each is a code set's folder's last element made safe, or that and `~` and an occurrence id, and names a set of code, not a document and not a file. It names no path of the archive, neither the set's folder nor any member's, and no text. So the record amends ADR-274 §8's *only numbers and enumerations* by this one method of two such names, and its rule that no line names a document stands.

**A tree drawn again** over a run with a set the file renamed gives that set its default name. Its folder of the earlier name in `code/` is one this drawing did not write, counted on the closing line as left behind by ADR-296 §6.3, and `code.csv` and the index name the set by its new folder.

## Consequences

- **A Profile row is one line**, its title, its key and its control, where it was its control and seven lines at least; what it does, what a change costs and its reports are one press of ▸ away, and its explanation and provenance a pointer's rest on the title.
- **The operator writes no provenance in the window.** A value changed there is saved with `set in the control panel`; a provenance written by hand in `profile.yaml` stays until its value is changed in the window.
- **A row stays open while the operator works in one working directory**, through Saves and Resets, and the rows of another start closed.
- **The texts the operator reads are one file**, `profile-texts.json`, and the cost line and its warnings one table each, so a word changes in one place and the tests hold every text to the same rules.
- **A report reads by one title everywhere**: its page, its tab and every link to it.
- **Every cut line of the window says it is cut**, with "…", and still copies whole.
- **A list reads as its items**, each removed by itself, and is added to with Enter.
- **Two windows cannot write over each other's `codeSetFolders`** unseen: the second Save is refused, as a row's is.
- **The Code sets section is the folders outside the corpus root**, the one thing the operator sets there; the code sets under the root are stage 1's to find and their folders' to name.
- **A tree drawn again renames in `code/` a set the operator had renamed**, to its folder's name, tells it in one line, and counts the old folder as left behind; a working directory's `code-set-names.yaml` stays and changes nothing.
- **Record my answers records the working directory's label file alone**; a label file kept elsewhere is recorded from the command line, `vespera label <file>`.
- **The closing line loses its clause of dormant names**, and the generation step its warning of a refused names file.

## Known limits

- **A provenance cannot be copied from the window**: a tooltip is not copied (ADR-364 §8), and no line shows it. It is copied from `profile.yaml`.
- **A provenance shows only while the pointer rests on the title**, so a row does not say at a glance which values the operator set by hand.
- **The tooltips are long**, the longest some 300 words; JavaFX's tooltip wraps them at the width the stylesheet gives it and shows them for as long as the pointer rests.
- **A list item holding a space or a comma cannot be a tag**: the pieces split it, as `ProfileEdit` reads a list today.
- **A set the operator had renamed takes its folder's name**, told once in a line of the output; a tree drawn into a new Output folder, which holds no earlier `code.csv`, tells nothing, its old tree keeping the old name.
- **The line of a set's folder changing is told for any change but one of case**, a `~` and an occurrence id gained or lost among them, and not only for a rename undone. **A change of case alone is told nothing on any file system**: on one that does not fold case, the new folder stands beside the old, which is counted as left behind and named by no line.
- **Two code sets whose folders end alike** are told apart by `~` and an occurrence id alone, which the operator can no longer replace with a name.

## Alternatives refused

- **A provenance line beside each value, with a link that opens it in an editable box.** The operator writes no provenance in the window, and a line on each row would take the room the compact tab gives back.
- **The provenance written by Vespera itself, with who, when and from which tab.** ADR-343 refused a provenance dated or naming the user, which would make every save a change of each provenance.
- **A row stacked over several lines, its description, cost and reports always shown.** It is the length the operator wanted shortened.
- **The Profile tab as one table of four columns, setting, value, why and what a change redoes.** The cost shrinks to a fragment there, and a list's tags and a folder's Browse do not fit a cell.
- **A list of keys beside one pane showing the selected key whole.** One key at a time hides the values the operator compares across rows.
- **The texts as constants of `ProfileKey`.** Some 30 KB of the operator's prose would sit among the key's type and runs, and a change of a word would be a change of the enum.
- **The texts as a `.properties` file.** Its escapes and its line continuations make a long text hard to read and to compare with what was settled, and the control panel already reads JSON.
- **The tooltip naming its key.** The key stands beneath the title, in brackets.
- **The open state forgotten at each Save.** A Save rebuilds every row, so the row the operator was reading would close under the pointer.
- **The cost line as the stage names**, *A change makes again: …*. It names the work by words the operator does not use.
- **A time on the cost line.** Any figure is one measurement of one corpus, and reads as a promise for every other.
- **Report links reading the file name.** A file name is the jar's, and the title is what the native view's tab reads.
- **A link's title of the window's own, beside the page's.** The page, its tab and the link would say three things of one report.
- **The log line naming the set's folder in the archive.** It is a path of the archive, which ADR-274 §8 keeps out of the lines; the two folders of `code/` say what moved.
- **The log line told as `CodeCopies` reads the earlier listing.** A drawing that fails before its listing is moved would tell a change the next drawing tells again.
- **Two names compared exactly.** *Core* and *core* are one folder where the tree usually lies, and the line would tell a change the operator cannot see.
- **The jar reading `code-set-names.yaml` to tell the renames it no longer applies.** Its renames are no longer read, as decided, and the tree's own listing says where each set stood.
- **The jar still reading `code-set-names.yaml` while the window stops writing it.** A set would carry a name nobody could change from the window, and the drawing two sources of a set's name.
- **The file deleted, or a warning on each invocation while it is there.** The file is the operator's, and a line repeated for a file that changes nothing is noise; the README says it once.
- **A folder under the corpus root kept as an entry with no name.** It writes nothing and changes nothing, so the section would list folders that do nothing.
- **A tag removed by a click on its text.** A click on the text selects it, to be copied.
- **The label file kept as a field, or moved to the Inclusions tab.** The operator answers in the window by folder, and a file kept elsewhere is the command line's.
