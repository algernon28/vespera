## Context

ADR-211 settled the six classes ADR-209 §2 named, each of which held a set of every survivor of a run, and widened to stage 3's map of distinct hashes and the seed/corpus comparison's corpus rows. While settling them its analyst found one more site, stage 2's resume set, and made no wider survey. #458 asks for that survey: every collection in `src/main` that grows with the corpus, whether of survivors, of occurrences, of rows of a table with a row for each occurrence, or of distinct values over them; a replacement measured for each; and a record of what is decided, with tests.

**How the survey was made.** Every class under `src/main`, read at `96a2cec`, for three things: a `jdbcTemplate.query`, `queryForList` or result set whose rows are kept rather than handed on; a collection built in a loop over the survivors, a walk's occurrences or a run's rows; and a string or page built whole before it is written. Each was followed to what it is fed, and kept as a site where what it holds grows with the number of occurrences, survivors or rows of a run, or with the distinct values over them. A collection that grows with one occurrence's content (a file's lines, one occurrence's shingles, one occurrence's chunks or pictures), with the seed set, with the runs, or with a fixed window, is listed in §9 and is not a site.

## Measured

**Units.** As in ADR-211: a size of heap is at 10⁶ bytes to the MB. No temporary file was measured for this record.

**The probes.** Throwaway programs outside the repository, run on 2026-10-09 with Java 21, the only JDK on the machine they ran on, and the sqlite-jdbc the pom carries, 3.53.2.1, on Linux, in a container, on whatever disk backs it, with the file cache warm and connections opened with the shipped URL's settings (`foreign_keys=on`, the write-ahead log, `synchronous=NORMAL`). ### Stage 2's resume set (rows 4 and 5)

A walk of N occurrences; a stage-1 run with every tenth `broken`; a stopped stage-2 run that measured the first half of stage 1's survivors in id order, as committed chunks do, with every tenth, five on, ruled out `degenerate-output` in that half, and a fault row for one occurrence in a hundred of that half. Older stage-2 runs, where present, measured every one of stage 1's survivors, as the table keeps after a run id moves. Three ways of yielding the survivors the stopped run has not recorded, each made twice in a pass as the reader and the processor's counter make it:

- **A**, today's: every occurrence recorded under the run read into a set, then the survivors gone through and each tested against it;
- **C**: the survivors read a page of 1,000 at a time, and for each page one statement asking which of its occurrences have a metric row under the run, by key;
- **D**: the survivors and the run's metric rows each read a page at a time in occurrence order, and merged.

| Occurrences, survivors of the stopped run, recorded | Older stage-2 runs | A | C | D | Statements, C / D | One set of A |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 100,000, 85,000, 45,000 | 0 | 0.51–0.56 s | 0.38–0.56 s | 0.25–0.33 s | 170 / 92 | 2.8 MB |
| 300,000, 255,000, 135,000 | 0 | 0.99–1.04 s | 1.06–1.19 s | 0.74–0.81 s | 510 / 272 | 9.7–9.8 MB |
| the same | 3 | 1.06–1.15 s | 1.06–1.37 s | 0.60–0.86 s | 510 / 272 | 9.7 MB |
| the same | 10 | 1.06–1.14 s | 1.20–1.45 s | 1.10–1.24 s | 510 / 272 | 8.6 MB |
| 1,000,000, 850,000, 450,000 | 0 | 2.77–2.99 s | 3.52–3.80 s | 2.37–2.40 s | 1,700 / 902 | 33.7 MB |

- **The answers were the same** in every round: 45,000, 135,000 and 450,000 survivors still to read, by each form, in both passes.
- **A holds 62 to 75 bytes an id, and holds it twice an invocation**: the reader reads the set, and the processor reads it again for its counter.
- **The plans.** C's ask: `SEARCH extraction_metric USING COVERING INDEX sqlite_autoindex_extraction_metric_1 (occurrence_id=? AND run_id=?)`. D written with `run_id = ?`: `SEARCH extraction_metric USING INDEX extraction_metric_by_run_id (run_id=?)` and `USE TEMP B-TREE FOR ORDER BY`, the run's rows sorted for every page, 0.84 to 0.91 s at 100,000; written with `+run_id`, as in the table: `SEARCH extraction_metric USING COVERING INDEX sqlite_autoindex_extraction_metric_1 (occurrence_id>?)`, a range of an index that holds every run's rows.
- **D was the quickest at every size, and grew the most with the runs the table keeps**: from 0.74–0.81 s to 1.10–1.24 s at 300,000 occurrences with ten older runs, where C went from 1.06–1.19 s to 1.20–1.45 s. D's page goes through every run's entries for its range of ids; C's ask is a lookup by key. `extraction_metric` gains a run each time stage 2's id moves, which it has done with most records since ADR-207.
- **The faults, paged by row number**: `SELECT rowid, occurrence_id FROM extraction_fault WHERE run_id = ? AND rowid > ? ORDER BY rowid LIMIT 1000` is planned `SEARCH extraction_fault USING INDEX extraction_fault_by_run_id (run_id=? AND rowid>?)`, with no temp B-tree. 5,000 fault rows took 0.001 to 0.002 s in six statements, and 0.002 s as one read into a set.

### Stage 4b (rows 8 to 15)

A stage-4 ledger of N occurrences, each with 200 distinct shingles under `word:5`, three in ten of them drawn from a pool of hashes so that hashes recur; every fiftieth occurrence a near-duplicate of the one before it, 180 of its 200 shingles shared, a Jaccard of about 0.82; every fiftieth, twenty-five on, wholly contained in the one before it, 120 of its 200. Stage 3's frequency rows written by ADR-211 §3's grouping; 128 MinHash values and sixteen bands of eight for each occurrence; `shingle_by_hash` built, as 4b builds it. The shingle-set cache was the shipped one, with its budget of 16 Mi hashes, which held every set at these sizes.

### 2. Stage 2 resumes a page of survivors at a time

**What the reader yields.** `pipeline.UnrecordedOccurrences` keeps no set. It is built over the survivors and a question, `UnrecordedOccurrences(Iterable<OccurrenceId> survivors, Function<Collection<OccurrenceId>, Set<OccurrenceId>> recordedAmong)`: it gathers the survivors into pages of up to 1,000, the ledger's own page, in the order they come; asks `recordedAmong` once for each page; and yields the page's occurrences it does not answer, in order. It holds one page. `ExtractionJobConfiguration.extractionReader` builds it with `page -> extractionMetrics.recordedAmong(run, page)`.

**The question.** `extraction.ExtractionMetrics.recordedAmong(RunId runId, Collection<OccurrenceId> occurrences)` answers a `Set<OccurrenceId>`: those of the given occurrences that have an `extraction_metric` row under `runId`. One statement for each 1,000 it is given, `SELECT occurrence_id FROM extraction_metric WHERE run_id = ? AND occurrence_id IN (?, …)`, planned as a lookup by the primary key; none for an empty collection. It is `extraction`'s, over `extraction`'s table.

**The count.** `UnrecordedOccurrences.countOver(Ledger ledger, RunId run, Function<Collection<OccurrenceId>, Set<OccurrenceId>> recordedAmong)` goes through `ledger.verdicts().survivors(run)` the same way and counts what it would yield. `ExtractionItemProcessor` keeps its one timed span, `counting the survivors still to read`, and inside it asks `ledger.verdicts().survivorCount(run)` where `extractionMetrics.metricRowsUpTo(run)` is empty and `countOver(ledger, run, page -> extractionMetrics.recordedAmong(run, page))` where it is not. It reads no set.

**What the resume line counts.** `ExtractionMetrics.occurrencesForRun`, both forms, goes. `ExtractionMetrics.recordedCount(RunId runId, ExtractionStatementProgress progress)` returns a `long`: it runs the statement `occurrencesForRun` ran, `SELECT occurrence_id FROM extraction_metric WHERE run_id = ?`, counted through `StatementSteps.counted` as `RECORDED_OCCURRENCES` with its 5 steps a row, and counts the rows it reads, holding none. Its lines are ADR-199's, unchanged. The reader wraps the survivors in `UnrecordedOccurrences` where that count is above zero, and the line `Stage 2 (extraction) resumes run <id>: occurrences already measured by committed chunks: <n>; faulted occurrences read again: <m>` takes `<n>` from it.

**The faults, a page at a time.** `ExtractionFaults.occurrencesForRun`, both forms, goes. `ExtractionFaults.eachPageOfFaulted(RunId runId, ExtractionStatementProgress progress, Consumer<List<OccurrenceId>> page)` returns how many it handed over, as a `long`. It reads the run's fault rows a page of up to 1,000 at a time, `SELECT rowid, occurrence_id FROM extraction_fault WHERE run_id = ? AND rowid > ? ORDER BY rowid LIMIT 1000`, planned by `extraction_fault_by_run_id (run_id=? AND rowid>?)` and sorting nothing; hands each page that holds a row to `page` once its statement has finished and before the next is issued; and tells `progress` `statementStarting(FAULTED_OCCURRENCES, faultRowsUpTo(runId))` once before the first page, `rowsRead(FAULTED_OCCURRENCES, <rows read so far>)` after each page that held a row, and `statementEnded(FAULTED_OCCURRENCES)` once after the last, on every path but one that throws. `stepsTaken` is not called. `ExtractionStatement.FAULTED_OCCURRENCES` declares no steps a row. The reader gives it `page -> ledger.verdicts().discardVerdictsAgainst(run, page, EXTRACTION_FAILED)`, then calls `discardForRun` as now: the verdicts that resolved a page's faults go before the next page is read, and the fault rows, by which the pages are found, only after the last. `<m>` in the resume line is the number it returns.

**Why a page at a time and not one statement.** Deleting a page's verdicts goes through the ledger's template, so it cannot run inside a counted statement's callback (ADR-193 §2), and the verdicts cannot be deleted by one statement that names `extraction_fault` (ADR-209 §3). Each statement finishes before the next begins.

**What it costs**: the resume's two passes over the survivors at 0.7 to 1.4 times today's time; a page held where today's held every recorded id twice (Measured).

### 3. The census compares two walks a page at a time

**`ledger.Occurrences.sameOccurrences(WalkId earlier, WalkId later)`** answers whether the two walks recorded the same occurrences. It reads a page of up to 1,000 of each walk in id order, `SELECT id, path, size_bytes, last_modified, creation_time FROM file_occurrence WHERE +walk_id = ? AND id > ? ORDER BY id LIMIT 1000`, planned by the integer primary key as ADR-211 §8 plans every page of a walk; compares the two pages row by row on the path, the size and the two times, the ids aside; answers `false` at the first page where they differ, in length or in any row, and `true` when both walks end on the same page. It holds two pages. **`Occurrences.occurrencesForWalk` goes**: nothing in `src/main` reads it but the comparison, and it hands a caller the whole walk.

**`corpus.AnomalyLog.sameAnomalies(WalkId earlier, WalkId later)`**, package-private as `anomaliesForWalk` is, does the same over `walk_anomaly`: `SELECT id, path_rendering, kind, detail FROM walk_anomaly WHERE walk_id = ? AND id > ? ORDER BY id LIMIT 1000`, planned by `walk_anomaly_by_walk_id (walk_id=? AND rowid>?)`, compared on the path rendering, the kind and the detail. **`AnomalyLog.anomaliesForWalk` goes.**

**`WalkRecorder.sawTheSameThing`** is `sameOccurrences && sameAnomalies` and the directories entered, as now.

**The order compared is the id order.** Today's lists came in the order the planner chose, size then id for the occurrences, and two lists are equal only in the same order. The pages are compared in id order, which is the order the walk recorded them. Two walks that recorded the same rows in another order are now called different and the later is kept, the direction that discards nothing; today they were called different too, unless every size that two of them share came in the same order.

**What it costs**: 0.3 to 0.6 times today's time, two pages held where two whole walks were (Measured).

### 4. Stage 4b goes through its signed occurrences a page at a time

`RedundancyResolution.resolve` keeps its signature and what it writes. What it holds:

**The signed occurrences are counted, and read a page at a time.** The counted read `SIGNED_OCCURRENCES` keeps its statement, its 5 steps a row and its lines, and counts the rows it reads, holding none; a run with none signed returns before anything else, as now. Where the passes below go through the signed occurrences they read them a page of up to 1,000 at a time, `SELECT rowid, occurrence_id FROM minhash_signature WHERE run_id = ? AND rowid > ? ORDER BY rowid LIMIT 1000`, planned by `minhash_signature_by_run_id (run_id=? AND rowid>?)`.

**Phase 1, the candidate pairs, a page at a time.** For each page of signed occurrences, one statement: `SELECT DISTINCT a.occurrence_id, b.occurrence_id FROM signature_band a CROSS JOIN signature_band b ON b.run_id = a.run_id AND b.band_ordinal = a.band_ordinal AND b.band_hash = a.band_hash AND b.occurrence_id > a.occurrence_id WHERE a.run_id = ? AND a.occurrence_id IN (?, …)`: every pair sharing a bucket whose lesser member is in the page, once. `CROSS JOIN` fixes the order SQLite reads the two in (Measured). Each pair is scored as now and unioned at or above the cut, and the page's pairs are let go before the next page is read. Every pair is found exactly once, in the page of its lesser member. The order pairs are scored in changes; the components do not, a union being the same in any order.

**The components hold the occurrences of the pairs at or above the cut, and nothing else.** `UnionFind` is built empty and takes an occurrence the first time a union names it; `components()` answers what it holds, each component two or more. Every occurrence it holds is in a component, so none is filtered out.

**The profiles are read as now, in statements of at most 1,000.** Once every page's pairs are scored, the profiles of every component's members are read, as today, and held with the components (§9), so the order the counters are announced in, profiles, then components and verdicts, stays ADR-192's. `ExtractionMetrics.alphanumericCharCounts` asks in statements of at most 1,000 occurrences, none for an empty collection, where today it named every member in one. The timed read of the near-duplicates' extraction metrics keeps its two lines, which now span those statements.

**Phase 2 asks what phase 1 removed.** No set of removed occurrences is kept. For each page of signed occurrences, one statement asks which of them phase 1 removed, `SELECT occurrence_id FROM redundant_with WHERE run_id = ? AND relation = 'near-duplicate' AND occurrence_id IN (…)`, the stage-4 run's own rows. `redundant_with` is `similarity`'s. A containment verdict phase 2 writes is not asked about, as today it never entered the set.

**An occurrence's rarest shingles, with its own rows.** No map of frequency rows is held. For each occurrence A not removed, one statement: `SELECT f.shingle_hash FROM shingle s JOIN shingle_document_frequency f ON f.run_id = ? AND f.shingle_parameter_identity = s.shingle_parameter_identity AND f.shingle_hash = s.shingle_hash WHERE s.occurrence_id = ? AND s.run_id = ? AND s.shingle_parameter_identity = ? GROUP BY f.shingle_hash ORDER BY f.document_count, f.shingle_hash`, the stage-3 run, A, stage 2's run and the granularity. Its rows are read in order, a hash in the boilerplate set passed over, until 32 are taken or the rows end: the same hashes, in the same order, that today's sort of A's distinctive set by the map gives, a hash with no frequency row being in neither. Both tables are `similarity`'s.

**Which candidates are signed and which were removed** is asked for A's candidates other than A, in one statement each, of at most 1,000 occurrences: `SELECT occurrence_id FROM minhash_signature WHERE run_id = ? AND occurrence_id IN (…)`, and the question of removal above.

**The raw counts stay remembered, within the cache's budget.** A candidate's raw count of shingle rows is remembered for the pass, as #277 has it, but in `ShingleSetCache` beside the sets, each count charged 10 hashes of the 16 Mi hash budget, the 75 bytes a map entry was measured to hold at 8 bytes a hash rounded up, the least recently used evicted first, sets and counts alike. At the sizes measured the budget holds every set and every count, and nothing changes.

**The reads that go.** The timed reads of the signature bands and of the shingle document frequencies: each was one statement over the run and is now one a page of signed occurrences or one an occurrence, inside a loop that reports. `SimilarityStatement` loses `SIGNATURE_BANDS` and `DOCUMENT_FREQUENCY`, and keeps `NEAR_DUPLICATE_METRICS`.

**The candidates counter counts signed occurrences.** How many pairs there are is known only once the last page has been read, so the counter `Stage 4b (redundancy resolution, near-duplicate candidates)` counts signed occurrences: `ResolutionProgress.toScorePairs(long)` keeps its name and is told the count of signed occurrences, once, before the first page's pairs are found; and `pairScored()` is replaced by `candidatesScored()`, told once for each occurrence of a page after every pair of the page has been scored, so a page's thousand are told together. An item is a signed occurrence whose candidate pairs, as their lesser member, have been scored. The containment counter is told the count of signed occurrences, as now.

**What it costs**: the pairs at the map's time or less; containment at 1.8 to 2.0 times today's time (Measured), which §12 question 6 puts to the operator. What it holds: a page of signed occurrences and its pairs, one occurrence's rarest shingles and candidates, the shingle-set cache within its budget, and the components (§9).

### 12. Questions put to the operator, and the answers

Each was put with the analyst's recommendation. The operator answered all six on 2026-10-09: the first, fourth, fifth and sixth by accepting the recommendation, the second and third by delegating them, the recommendation being taken.

1. **The relevance report's sample (row 17).** The bands and the candidate cuts can be counted a page at a time with nothing an operator reads changing (Measured: 1.55 to 1.91 s against 2.42 to 2.65 s at a million scored, sixty held against 49 bytes a scored occurrence, read twice). The sample cannot: ADR-088's draw shuffles each band whole with a generator seeded from the run id, and no bounded pass reproduces a shuffle. Refused, the report holds every scored occurrence of the run, and this record says so as the reason. **Answered: accepted.** §13 is the decision.
2. **Stage 1's unrecognised leading bytes (row 3).** The format-mix page shows a row for each distinct four leading bytes among the files stage 1 could not recognise, each with its exact count (ADR-095). ### 13. The relevance report reads a page of scores at a time, and each band gives its twelve of least key

By the operator's answer to §12's question 1. `RelevanceDistribution` holds no list of the scored occurrences, and `LabelledSpread` is handed none.

**`measure(RunId run)`** makes two reads. **The range**: one statement, `SELECT MIN(score), MAX(score), COUNT(*) FROM relevance_score WHERE run_id = ?`; where the count is nought it throws `NoSuchElementException`, as `orElseThrow` does today, and the report's gate reads that as before. **The bands and the draw**: one read of the run's scores a page of up to 1,000 at a time, `SELECT rowid, occurrence_id, score, winning_seed_occurrence_id FROM relevance_score WHERE run_id = ? AND rowid > ? ORDER BY rowid LIMIT 1000`, planned by `relevance_score_by_run_id (run_id=? AND rowid>?)` and sorting nothing. Each score is put in its band by `bandOf`, the lowest and the width taken from the range, as now; each band counts its scores and keeps the twelve of least key it has met, no more.

**The key.** The key of an occurrence in a band is SplitMix64's finaliser applied to the band's seed exclusive-or the occurrence's number, `z = (z ^ (z >>> 30)) * 0xbf58476d1ce4e5b9L; z = (z ^ (z >>> 27)) * 0x94d049bb133111ebL; z ^ (z >>> 31)`, compared as an unsigned number. The band's seed is the one the shuffle was seeded with, `seedFor(run, band)`: the run id's UTF-8 bytes folded by 64-bit FNV-1a, plus the band's ordinal. The finaliser and the exclusive-or are each one to one, so no two occurrences of a band share a key and no tie is broken. The order the rows come in decides nothing.

**What comes back** is today's `Distribution`, field for field: the count; the lowest and the highest; each `Band` with its bounds, its count, how many it gave and its shortfall; and the sample, the bands lowest first, each band's twelve in ascending order of key. **What changes is which twelve**, against the shuffle's for the same run; ADR-088's rule that the same run always asks about the same sixty stands. The answers already given are keyed by path and stay (ADR-097, ADR-169).

**`spreadOf(RunId run, Map<OccurrenceId, Boolean> answers)`** takes `measure`, then one more paged read of the run's scores, handed to `LabelledSpread.of(Distribution, Iterable<Scored>, Map<OccurrenceId, Boolean>)`, which goes through them once, counting each band's answers and every candidate cut's documents and answers on either side of it in the one pass, where today it went through a held list once for the bands and once for each cut. `scoredUnder(RunId)` answers that `Iterable`, each iterator starting at the first page. The spread is the one today's code gives over the same rows.

**What the report holds**: the sixty drawn and five counts, where it held every scored occurrence twice (Measured: 49 bytes a scored occurrence a read). Its lines, `reading the scores` and `reading the scores against the answers`, are unchanged, each now spanning a paged read.

### 14. A stage-2 fault is written where its set-aside is heard, and resolved a page at a time

By the operator's answer to §12's question 4. **The rule ADR-139 §3 gives stands**: only a step that completed resolves its faults, each into `extraction-failed` with the reason `category: detail`. **ADR-139 §2's mechanism is replaced.** It held every fault until the step ended, because writing one where the skip is heard was taken to need a second connection beside the chunk's. Read in spring-batch-core 6.0.5's source, `ChunkOrientedStep` hears a skip in processing inside the chunk's own transaction, on the step's thread, so a row written there goes on the chunk's connection; `ASetAsideIsHeardInsideItsChunksTransactionTest` holds that of the library the build ships, and fails the day an upgrade hears a skip elsewhere.

**`extraction.ExtractionFaultResolution` holds no collection.** `record(OccurrenceId occurrence, RunId run, String category, String detail)` writes the fault row at once, through `ExtractionFaults.write`, on whatever transaction its caller holds; `nothingRecorded()` says whether any was recorded by this instance. `hold`, `nothingHeld` and the `Held` record go.

**`resolve(RunId run, boolean completed, FaultResolutionProgress progress)`.** Where the step completed: `toResolve` once, with the number of the run's fault rows, `ExtractionFaults.countForRun`; then the run's fault rows read a page of up to 1,000 at a time by row number, `SELECT rowid, occurrence_id, category, detail FROM extraction_fault WHERE run_id = ? AND rowid > ? ORDER BY rowid LIMIT 1000`, through `ExtractionFaults`; for each row a verdict, `extraction-failed`, `category: detail`; `faultResolved()` after each. Where it stopped: nothing is written and nothing is told, the rows already standing. The two-argument form calls it with `FaultResolutionProgress.NONE`, as now.

**`pipeline.ExtractionFaultRecorder`.** `onSkipInProcess`, for a `ServiceScopeFailureException`, calls `record(item, stageRuns.extraction(), category, detail)`: the run is the one the reader asked for before it yielded the item, so asking mints nothing and calls nothing (#319). `afterStep` returns at once where nothing was recorded, as it does today where nothing was held; otherwise it resolves in a transaction of its own, as now, telling the counter `Stage 2 (extraction, faults resolved)` only where the step completed.

**What changes in what is kept.** A fault row commits with its chunk, and a chunk that rolls back takes its fault rows with it, its occurrences being read again by the next invocation. A stopped invocation, or a process that is killed, leaves the fault rows of every committed chunk, where it left them only if `afterStep` ran; a resume reads them a page at a time, deletes the verdicts they resolved and reads their occurrences again (§2), as it already does. **A chunk rolls back only where the step stops.** The step skips `ServiceScopeFailureException` and nothing else, and only `ExtractionItemProcessor` throws it, in processing; spring-batch-core 6.0.5 goes over a chunk's items again in transactions of their own, its scan, only where the write's failure is skippable, so a write that fails stops the step, and no scan writes a chunk again without its fault rows. Its occurrences, their fault rows gone with the chunk, are read again by the next invocation, as unrecorded. An occurrence set aside twice under one run in one invocation would meet the fault table's key, as the held list met it at the step's end; nothing found makes that happen.

**What it holds**: one fault at a time, and a page of fault rows at the end, where it held every fault of the step (Measured: 193 bytes a fault).
