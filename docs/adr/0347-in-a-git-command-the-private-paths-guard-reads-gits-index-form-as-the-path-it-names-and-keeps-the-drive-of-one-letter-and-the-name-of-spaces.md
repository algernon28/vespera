# ADR-347 — In a git command the private-paths guard reads git's index form as the path it names, and keeps the drive of one letter and the name of spaces

- **Date**: 2026-11-04
- **Status**: accepted on 2026-11-04.
- **Amends**: [ADR-217](0217-on-windows-the-private-paths-guard-reads-every-path-as-windows-opens-its-names-without-the-dots-spaces-and-stream-name-that-end-each.md), in these places and no others:
  - §2, "a name made only of dots, spaces or a stream name is refused": in a segment whose program is `git`, a token that begins with git's index form, `:<path>` or `:<N>:<path>`, is read as its path, so the empty name before its colon is no longer such a name (§1 below);
  - its Consequences' first item of harmless commands refused, "a token that begins with a colon", for that one form and for a refspec that deletes a branch, which takes the same reading (§2 below);
  - its "Decided here" 5 and "What this does not decide", "whether the costs of §2 are kept": they are kept but for that form (§3 and §4 below).
- **Keeps**: [ADR-196](0196-no-agent-reads-the-operators-documents-and-an-allow-list-hook-that-fails-closed-refuses-every-other-path.md) §4, its "path on a drive with no separator after the colon", read on Windows from a token headed by one letter and a colon (§3 below); every other reading of §4, its bounds and §6. The rest of an index path is read by those readings, and by nothing looser. Its §5's list of what the hook does not cover gains §5 below, and nothing of it is struck.
- **Keeps**: [ADR-201](0201-the-private-paths-guard-reads-a-climb-out-of-a-link-both-ways-and-refuses-a-name-it-cannot-follow.md): the rest is read as text and as walked, and a name of it that is there and cannot be followed refuses.
- **Keeps**: [ADR-264](0264-the-private-paths-guard-refuses-only-what-reads-or-writes-outside-the-allow-list-and-a-working-directory-is-open-as-the-place-it-lies-in.md) §3: `git` is no lister, and the refusal "outside the allow list" is lifted for no reading this record adds. Its §3(a) cuts a command into segments, and §1 below cuts it the same way, but finds no git segment in a command where that cut may not be the shell's.

## Context

On Windows ADR-217 §2 refuses a name made only of dots, spaces or a stream name, since what Windows opens for one is not known. A token of a command that begins with a colon has such a name in front of it: read as a relative path, `:AGENTS.md` is one name, and with its stream name taken off it is empty. So `git show :AGENTS.md`, `git show :0:docs/x.md` and `git diff :2:src/a.java` were refused on Windows, from inside the checkout, though git reads nothing there but a blob of the repository's own index. ADR-217 named the cost and left open whether it is kept (its "What this does not decide").

The user was asked three questions and answered each:

1. Whether ADR-196's drive of one letter is loosened, so that `m:m.group` in a `python -c` lambda, and `Q:x`, are not read as a path on drive `M` or `Q`. **No: "KEEP ADR-196's one-letter-drive rule as it is: `m:m.group` and `Q:x` stay refused; nothing loosens it."**
2. Whether the guard accepts git's index form. **Yes: where a segment's program is `git`, a token `:<path>` or `:<N>:<path>`, N a stage number 0 to 3, has its leading `:` or `:N:` taken off, and the rest is judged as a path relative to the repository, still checked against the allow list like any path.** `git push origin :claude/x`, a refspec, and `sed ':a'` stay as ADR-217 has them unless this record decides otherwise for refspecs.
3. Whether a name made only of spaces, as `sed 's/ /_/g'` holds one between its slashes, is let through. **No: "a name made only of spaces stays refused; awk/sed programs go in a file."**

### Measured

### Read, and not executed

- The draft guard as amended at the gate, off Windows: for `git show ":."./outside/doc.txt` it reads the word git is given, `:../outside/doc.txt`, as written alone, and as written that is a folder `:..` inside the checkout, so it lets O707 through there.
- `git-bisect(1)`, `git-submodule(1)` and `git-rebase(1)`: `git bisect run <cmd> [<arg>...]` runs `<cmd>` and gives it the words after it; `git submodule foreach <command>` runs the words after `foreach` as a shell command in each submodule checked out; `git rebase --exec <cmd>`, or `-x <cmd>`, runs `<cmd>` as one or more shell commands after each commit it makes.

- `gitrevisions(7)`: ":[<n>:]<path> … A colon, optionally followed by a stage number (0 to 3) and a colon, followed by a path, names a blob object in the index at the given path." A stage number of 4 or more makes no stage form, and `:4:x` is the path `4:x`.
- PowerShell's `about_Quoting_Rules` and `about_Parsing`: PowerShell takes the typographic quotes ‘ ’ ‚ ‛ as single quotes and “ ” „ as double quotes, and after the stop-parsing token `--%` passes the rest of the line to a native command as written, a `;` among it, up to a line break or a pipe.

## Decision

### 1. In a git segment, a token that begins with the index form is read as its rest

The command is cut into segments as ADR-264 §3(a) cuts it, at `;`, `&&`, `||`, `|`, `&` and the line break, without regard to quotes. **A segment's program is `git`** where its first word is the bare word `git`: no separator in it and no quotes around it, compared character for character in a Bash command and with its case folded in a PowerShell command, as ADR-264 §3(d) compares a lister. An assignment before it, a word that runs another program (`env git`, `command git`), `git.exe` and a path to git are not `git`. **A command that holds `(`, `)` or a backtick, or in PowerShell `{` or `}`, has no git segment**, as ADR-264 §3(b) holds of a listed command: a substitution can run another program inside the segment, and that program would be given the reading.

**Nor has a command whose cut may not be the shell's.** For a list of listers a cut in too many places fails closed, since each segment must be a lister and a piece of one is not. Here it fails open: a cut inside quotes makes the words after a quoted `; git` a git segment, and the shell gives them to another program. So a command has no git segment when:

- **a segment break falls inside a quoted string**: a `;`, `&`, `|`, CR or LF between a quote and the quote that closes it, the quotes paired from left to right, `'` with the next `'` and `"` with the next `"`;
- **a quote is left unpaired** by that pairing;
- **in a Bash command, a backslash stands directly before a quote, a `;`, `&` or `|`, a CR or a LF**: the escaped quote is no quote to the shell, the escaped break is a character of a word, and a backslash before a line break joins two lines into one command;
- **in a Bash command, it holds `<<`**, anywhere in its text, inside quotes or not, as `(`, `)` and a backtick are found: a here-document's lines, and a here-string's word after `<<<`, are text given to the program on the line of the `<<`, and a cut at their line breaks makes a git segment of a line Bash never runs. A PowerShell here-string, `@'` or `@"` with a line break after it, holds its line breaks between quotes, and so has no git segment by the first point;
- **in a PowerShell command, it holds a typographic quote** (‘ ’ ‚ ‛ “ ” „), which PowerShell pairs as it pairs `'` and `"` (Read, and not executed), **or the stop-parsing token `--%`**, after which a `;` is passed on as text.

So `cat "a; git show" :README.md`, `cat \' "x' ; git show" :README.md`, `cat a\; git show :README.md`, a line ended by a backslash before `git show :README.md`, and `xargs cat <<EOF` with a line `git :README.md` before its `EOF` give `:README.md` no reading, and it is refused on Windows as ADR-217 §2 has it. **So is `git commit -m "a;b" && git show :README.md`**, in which git is given both: the `;` inside the message's quotes leaves the command with no git segment. A quoted string that holds no break, as in `git commit -m "fix it" && git show :README.md`, takes nothing away.

**In a git segment, a token that begins with `:` is read as its rest**: the token with its leading `:<N>:` taken off, where N is one digit from 0 to 3, or else with its leading `:` taken off. A token here is **a word of the segment that the shell's punctuation and white space end and that holds no quote, read from the word's start, or a word that is one quoted string and nothing else, read whole**, as ADR-196 §4 reads each. Every other word that holds a quote gets no reading (below), a word that begins with a quoted string and goes on, as `":a"b`, among them. **The rest is read as every token of the command is**: a drive path, a bare drive, a drive of one letter with no separator after the colon on Windows, a home path, a variable at its head, a Git Bash or UNC path, and otherwise a relative path, read against each folder the command names (ADR-196 §4), as text and as walked (ADR-201 §1), and on Windows as Windows opens its names (ADR-217 §1). The rest is cut at `,`, `{` and `}` as any token is, and each piece of it read as ADR-217 has it. Each reading is judged by the allow list, its `read` lines, the closed `.claude` folders, a deliverable tree's marker and every other check as any path's is. An empty rest is no path, as a token left empty by trimming its punctuation is none.

**Where the rest, read whole, records no path, the token is read as written as well, on every platform**, as every token was before this record, and ADR-217 §2 and the allow list judge it. **Read whole** is the rest's text read as one token, not cut at `,`, `{` or `}` and not split at `=`, and in a Bash command where a `${NAME-word}` in it makes two readings of it, each of those; the rest records a path only where each such reading does. Its pieces and its value after `=` are still read and judged as above, but one of them that records a path does not stand in the place of the token as written: none of them is the word git is given. A rest records no path where ADR-196 §4 reads it as none: a rest that begins with `-`, as an option does, or with `/` or `\`, a path rooted on the current drive without its letter, a URL `x://`, or a rest headed by a variable that has no value. **An empty rest is under this rule**, and fails closed: `git show :0:` is read as `:0:`, a name made only of a stream name, and refused on Windows. A lone `:`, as in `git push origin :`, is no token as written either and is let through, as before this record. So `git commit -F :/../../outside/doc.txt`, `:0:/...`, `:-../../../outside/doc.txt`, `:$NO_SUCH_VARIABLE/../../outside/doc.txt` and `git show :https://h/../../../outside/doc.txt` are refused on every platform, each climbing out of the checkout as written, and `git commit -F :\..\..\outside\doc.txt` on Windows, where `\` separates names (O801 to O808). **So are those tokens with a piece or a value beside the climb that names a path inside the checkout**: `git commit -F :/../../outside/doc.txt,x`, `:/../../outside/doc.txt{,x}`, which Bash expands into O802's word and a second one, `:/../../outside,x/../outside/doc.txt`, `:/../../outside/doc.txt=x`, `:/../../outside=x/../outside/doc.txt`, `:-../../../outside/doc.txt=x`, `:$NO_SUCH_VARIABLE/../../outside/doc.txt,x`, `:0:/../../outside/doc.txt,x` and PowerShell's `':/../../outside/doc.txt,x'` on every platform, and `:\..\..\outside\doc.txt,x` on Windows; and `git show :/@{u}` is refused on Windows, whose rest is cut at its braces into a piece `u` (O809 to O819). **So are `git commit -F :${NAME-/../../outside/doc.txt}` and `:0:${NAME-/../../outside/doc.txt}` where `NAME` has a value that names a path inside the checkout**, on every platform: the value's reading records a path and the word's does not, so the rest records none (O820, O821). The reading only adds a refusal: what the rest names, where it names a path, is read as above, and a token whose rest names none keeps the refusals it had.

**On Windows the token is read as its rest and not as written**, but where its rest, read whole, records no path (above): as written, its first name is made only of a stream name and ADR-217 §2 refuses it, which is the cost this record lifts. **Elsewhere it is read both as written and as its rest, and either refuses**: as written it is the name ADR-217 §7 says a colon makes, read as before, and the rest adds a reading of the place git reads.

**These tokens of a git segment are not given the reading, and keep ADR-217 §2's refusal on Windows:**

- **the target of a redirect**: the word after a bare word that holds `<` or `>`, which takes in `>`, `>>`, `<`, `<>`, `2>`, `{fd}>`, PowerShell's `*>` and `*>>`, and a word with the operator written onto its end, as `:README.md>`; and a token that `<` or `>` stands directly before inside a word. The shell opens it, not git. A quoted `">"` is no operator;
- **a value after `=`**, which ADR-196 §4 reads as a token of its own: `git diff --output=:out.txt` names a file git writes by that name, and a value is not git's index form;
- **a token that does not begin a word**: a piece of a word cut at `,`, `{` or `}`, as `:b` in `git show :a,:b` and both members of `git show {:a,:b}`, which Bash expands into two words; and the path two halves joined at an escaped space make, as `git show :my\ notes/r.txt`, read as ADR-217 has it. The quoted form, `git show ':my notes/r.txt'`, is given the reading;
- **a word that holds a quote and is not one quoted string and nothing else**: a bare word with a quote inside it, as `:a"b"`, and a word that begins with a quoted string and goes on, as `":a"b`, each of which the shell gives git as `:ab`, and `":."./outside/doc.txt`, which it gives git as `:../outside/doc.txt`, a climb out of the checkout. The guard reads such a word in pieces, none of which is the word git is given, and gives none of them the reading. **It reads the word git is given too**, where that begins with `:` once the word's quotes are taken off and holds no other quote: **as written and by its rest, on every platform**, and either refuses. On Windows the reading as written refuses it, its first name being made only of a stream name (ADR-217 §2), so the word stays refused there (O704 to O706); elsewhere its rest is what refuses `:../outside/doc.txt` (O707), which as written is a folder `:..` inside the checkout;
- **a token that does not begin with the colon**: `HEAD:README.md` is read as before.

**Relative to the repository.** git reads a rest that begins with `./` or `../` from the current directory, and any other from the top of the working tree (Measured). The guard reads every rest against each folder the command names, the current directory and a `git -C` folder among them, as it reads every relative token. Where git runs in the top of its working tree the two are one place. Where it runs beneath it, git reads a name from a folder above the one the guard reads it against; that is §5's.

### 2. A refspec takes the same reading

A refspec that deletes a branch, `git push origin :claude/x`, is a token that begins with a colon in a git segment. **It is given §1's reading, and is let through where its rest, read as a path, lies inside the allow list**, as `claude/x` read from the checkout does. Telling a refspec from an index path needs git's grammar of each subcommand: `push` and `fetch` take refspecs, `show`, `diff` and `cat-file` revisions, `add` and `rm` pathspecs. That is a second parser to keep in step with git for no gain: a refspec reads no file, and reading it as a path can only refuse what that path refuses. `git push --delete` stays the form that names no path.

### 3. ADR-196's drive of one letter is kept

On the user's word (Context, question 1), a token headed by one letter and a colon is on Windows a path on that drive, in a git segment as anywhere. `python -c "f = lambda m:m.group(0)"` and `git show Q:x` stay refused on Windows. A rest that is such a token is read so too: `git show :0:Q:x` is refused, as is `git show :C:/x`, a drive path. A token that begins with a colon is not headed by a letter, so §1 and this section never meet on one token's head.

### 4. ADR-217's refusal of a name made only of spaces is kept

On the user's word (Context, question 3), "a name made only of spaces stays refused; awk/sed programs go in a file". A name made only of spaces that stands in a longer path is refused on Windows, as ADR-217 §2 has it: `sed 's/ /_/g' README.md`, `cat 'scratch/ /note.txt'`, and in a git segment the rest of `git show ': /x.md'`. ADR-217 §2's one exception, a relative token of a command made only of spaces, stands. A program for `sed` is written to a file and named with `-f`, and one for `awk` likewise.

`sed ':a'` and a JSON value written after its colon with no space, `echo '{"a":1}'`, are tokens that begin with a colon after a program that is not git, and stay refused on Windows.

### 5. What the hook does not cover, added to ADR-196 §5

- **A rest git reads from the top of a working tree that lies above the current directory.** The guard reads it from the current directory. It is the gap `HEAD:<path>` already has, read since ADR-196 §4 as a relative token `HEAD:...` and on Windows as `HEAD` with a stream name. What git reads by the index form is a blob of the repository it runs in, and git refuses a path outside that repository (Measured).
- **A token of a git segment that git opens as a file by its name as written**: an option's value given as the next word, as in `git commit -F :msg.txt`, or a path given to `git apply` or `git diff --no-index`. On Windows the guard reads the rest alone where the rest, read whole, names a path, and what Windows opens for a name that begins with a colon is not measured (ADR-217 §5); where the rest names none, the token as written is read too (§1). Elsewhere the token as written is always read too.
- **A token of a git segment that another program is given.** git runs other programs: an alias that begins with `!` hands the words after it to a shell command, whether the alias is set in the user's or the repository's configuration or by `-c alias.<name>=!<command>` or `--config-env` in the command itself (Measured), and the pager, a difftool, an external diff, a textconv filter and the hooks run programs of the configuration's choosing. Three of its subcommands run the command's own later words as a program (Read, and not executed): `git bisect run` runs the word after `run` and gives it the words after that, `git submodule foreach` runs the words after `foreach` as a shell command, and `git rebase --exec` or `-x` runs the word after it as one. In `git bisect run cat :README.md`, `cat` is given `:README.md`, and the guard reads only its rest on Windows. The shell can run another program by the name `git` too: a Bash alias or a function named `git` defined earlier in the command, PowerShell's `Set-Alias git`, or a `git` earlier on the `PATH`. Such a program may open the token as written. The rest is still read and judged by the allow list, and where it, read whole, names no path the token as written is read too (§1), so what is left open is ADR-217 §5's unknown, what Windows opens for a name that begins with a colon and whose rest names a path.
- **`:/<text>`**, which is a commit's message to `git show` and the pathspec's "from the top" to `git add`. Its rest begins with `/`, a path rooted on the current drive without its letter, which ADR-196 §4 leaves unread unless it is a Git Bash drive path, so the token is read as written (§1), whatever the pieces of a `<text>` cut at `,`, `{` or `}` read, as the `u` of `git show :/@{u}` (O819). On Windows its first name, `:`, is then made only of a stream name, and `git show :/<text>` and `git add :/<path>` are refused there, as ADR-217 §2 had them. Elsewhere it is read as a name `:` in each folder the command names, which is not what git reads by it: as a revision it names no path, and as a pathspec a path inside the repository from its top.
- **A rest that holds a brace list with text before or after it**, as `git commit -F :x{,/..}/../../outside/doc.txt`, which Bash gives git as `:x/../../outside/doc.txt` and `:x/../../../outside/doc.txt`, each of whose rests climbs out of the checkout. It is ADR-196 §5's gap, "a brace list with text before or after it", which `cat x{,/..}/../../outside/doc.txt` has open already: the rest read whole, its pieces cut at `,`, `{` and `}`, and on every platform but Windows the token as written are read, and none of them is either word Bash gives git. Read whole, `x{,` and `..}` are names that the two `..` after them take back, and the pieces `x`, `/..` and `/../../outside/doc.txt` name a path inside the checkout or none. On Windows ADR-217 §2's refusal of a name made only of a stream name refused every such token that begins with `:`, and so hid the gap for it there; this record lifts that refusal for git's index form, and so opens the gap there, in a git segment, as it is open for every other token (Measured). It is recorded, and not closed by reading as written a rest that holds a `{` with text after its `}`: ADR-196 §5 leaves the gap open for every token, and this record does not reopen it for one.

None of these has a case, on ADR-196 §4's ground that a case would hold the gap in place.

### 6. Elsewhere nothing changes

A token that begins with a colon after any other program, in a segment whose program is not git, or in a command with no git segment, is read as ADR-217 has it. A file tool's field and a search's path are not commands, and a name made only of a stream name in one stays refused on Windows (ADR-217 §2, Z303).

### 7. The test

## Decided here

1. **§1: the rest is read on every platform**, and elsewhere beside the token as written. The user's answer named the form, and Windows is where its cost fell; reading the rest elsewhere refuses what git reads outside the allow list there too.
2. **§1: a git segment is cut and recognised as ADR-264 §3 recognises a lister's**, a command holding `(`, `)` or a backtick, or a PowerShell brace, having none.
3. **§1: a redirect's target and a value after `=` are not given the reading**, a redirect's target being the word after any bare word that holds `<` or `>`.
4. **§1: the rest is read against each folder the command names**, and not against the top of the working tree, which the guard would have to find by asking the file system or git; §5 records the difference.
5. **§2: a refspec takes the index form's reading**, where the user left it as ADR-217 has it unless this record decided otherwise.
6. **§1: a command whose cut may not be the shell's has no git segment**: a break inside quotes, an unpaired quote, in Bash a backslash before a quote or a break or a `<<` anywhere, in PowerShell a typographic quote or `--%`. `git commit -m "a;b" && git show :README.md` goes this way and is refused on Windows, and so does a here-document's line that begins with `git`, which the draft as amended at the gate read as a git segment (O610).
7. **§1: a piece of a word cut at `,`, `{` or `}`, two halves joined at an escaped space, and every word that holds a quote but is not one quoted string and nothing else are not given the reading**: each is a token the guard reads apart from the word git is given. Only a word that is one quoted string alone is read whole. The draft as first built gives the reading to a word that begins with a quoted string and goes on, as `":."./outside/doc.txt`, and so fails open (O705, O706). **The word git is given for such a word, its quotes taken off, is read as written and by its rest on every platform**, beside the pieces and not in their place: finding it is a reading of the shell's quoting, which where it erred would lift a refusal if it stood in the place of ADR-217 §2's, and only adds one where it stands beside it. Reading it by its rest off Windows holds the Consequences' "a rest outside the allow list is refused on every platform"; the draft as amended at the gate read it as written alone, and off Windows let `git show ":."./outside/doc.txt` through (O707).
8. **§5: what git or the shell hands to another program is recorded, and refuses nothing more.** A refusal of the reading in a segment that holds `-c` or `--config-env` would close one spelling of a gap that the user's and the repository's configuration hold open whatever the command says, and the rest is judged by the allow list either way.
9. **§1: a token whose rest, read whole, records no path is read as written as well, on every platform, an empty rest among them.** The reading lifts ADR-217 §2's refusal in favour of the path the rest names; where the rest names none, nothing stands in that refusal's place, and the draft as amended a second time let a climb out of the checkout through on Windows (O801 to O808). An empty rest fails closed with the rest: `git show :0:` names no file, and costs nothing that is used. **The rest is asked this whole**, as one token, not cut at `,`, `{` or `}` and not split at `=`: a piece and a value after `=` are read beside the word and are not the word git is given, and where one of them stood in the place of the token as written, the draft as amended a third time let the same climb through on Windows with `,x`, `{,x}` or `=x` after it (O809 to O818), and `git show :/@{u}`, which §5 says is refused there (O819). **Of a `${NAME-word}`'s two readings, each is asked**, and the rest records a path only where both do: the token as written is the word git is given, whichever of them Bash makes, and where the draft as amended a fourth time counted the rest as a path when either did, it let the climb through on Windows with the value's reading beside it (O820, O821). Where the rest read whole names a path, the token as written adds no refusal but ADR-217 §2's: it climbs no further than the rest, and its pieces after the first and its value after `=` are the rest's own.

## Consequences

- **On Windows `git show :<path>`, `git show :<N>:<path>`, `git diff :<N>:<path>` and `git push origin :<branch>` run from the checkout**, where the rest lies inside the allow list.
- **A rest outside the allow list is refused on every platform**, `:../outside/doc.txt` and `:$HOME/Documents/x.txt` on Linux among them, where before they were names that began with a colon. **A token whose rest, read whole, names no path is read as written as well**, as before this record, so a climb out of the checkout as written, as `git commit -F :/../../outside/doc.txt`, is refused on every platform too (O801 to O808), and so it is with a piece or a value after `=` beside it that names a path, as `:/../../outside/doc.txt,x` (O809 to O818), and with a `${NAME-word}` whose value names a path and whose word names none (O820, O821).
- **On Windows these are still refused, each to be reworded as ADR-217 says**: a token that begins with a colon after any program but git, a JSON value written after `":` with no space, a `sed` label, a redirect's target or an option's value that begins with a colon, a token in a git segment whose rest, read whole, names no path, as `git show :/<text>`, `git show :/@{u}` among them, `git add :/<path>` and `git show :0:`, and any such token in a command that holds `(`, `)` or a backtick. So is `m:m.group`, `Q:x`, and a `sed` or `awk` program that holds a name made only of spaces between separators.
- **On Windows these are refused too, though git alone is given the token**: an index path in a command whose quotes hold a `;`, `&`, `|` or line break, as a commit message with a `;` does, or whose quote is unpaired or escaped; an index path in a Bash command that holds `<<`, a here-document or a here-string, wherever the `<<` stands; an index path in a brace or comma list; an index path whose space is escaped, which is quoted instead; and a word that holds a quote and is not one quoted string alone. A commit message is written with `-F`, or the `git show` run as a command of its own.
- **Nothing under `src/main` changes, and no run id moves.**

## Alternatives weighed

- **Refspecs kept refused** (§2). Rejected: it needs git's grammar of each subcommand, and the reading it would avoid only refuses more.
- **Reading the rest from the top of the working tree**, found by walking up to `.git`. Rejected for this record: it asks the file system before the allow list is judged, against ADR-196 §2, or starts git, which ADR-217 weighed and rejected for Windows; and it closes a gap `HEAD:<path>` has open already.
- **The reading for any program**, not git alone. Rejected: `cat :x` opens a name that begins with a colon, whose opening on Windows is not known (ADR-217 §2), and the user's answer named git.
- **Loosening the drive of one letter, or the name made only of spaces.** Refused by the user (Context, questions 1 and 3).
- **A cut that honours quotes and escapes**, so that `git commit -m "a;b" && git show :x` keeps its reading (§1). Rejected: it is a second parser of each shell's quoting, here-strings, `$'…'` and stop-parsing included, and where it errs it fails open. A command the guard cannot cut as the shell does is refused the reading, which costs a rewording.
- **Giving the reading to a piece, to joined halves and to a word that holds a quote but is not one quoted string alone** (§1). Rejected: a piece and two joined halves are read apart from the word the shell gives git, so the guard would give the reading to a text no program is given; and the word a quoted word gives git is found by taking its quotes off, a reading of the shell's quoting that would lift ADR-217 §2's refusal where it erred. That word is read beside its pieces, as written and by its rest, and never in their place (Decided here 7).
- **No reading in a segment that holds `-c` or `--config-env`** (§5). Rejected, Decided here 8.
- **A rest that holds `,`, `{`, `}` or `=` read as written as well**, whatever its whole text reads, as §1 treats a piece (Decided here 9). It closes O809 to O819 too, and is simpler to build. Rejected: it refuses on Windows an index path whose name holds a comma, a brace or `=`, as `git show :docs/a,b.md`, `git show :a=b.md` and `git show :src/{a,b}.md`, which the chosen reading lets through from the checkout (Measured), and adds no refusal that reading the rest whole does not make, since the token as written climbs no further than the rest read whole, and its pieces after the first and its value after `=` are the rest's own.

## What this does not decide

- Whether `git.exe`, a path to git, or `git` after `env` or an assignment is ever given the reading.
- What Windows opens for a name that begins with a colon, which ADR-217 left unmeasured.
- Whether ADR-217's other costs, a token of three dots and an elision in a quoted sentence, are kept.
