# ADR-075 — Stage 3 writes a confidence-distribution report that calibrates tier 2

- **Date**: 2026-09-05
- **Status**: accepted
- **Amends**: none (fills in the "report" half of ADR-019's "content census is derived columns plus a report," left unspecified)

## Context

ADR-019's reconstituted summary pairs two things: derived columns (settled — ADR-073, written during stage 2's own pass) and a report. Nothing said what the report computes, what it produces, or which decision it exists to inform.

**What already exists, read off the code rather than assumed.** `profile.ProfileValue` carries a `measurement` field, documented as "where the data informing this key lives... a walk, a table, a report" — the vocabulary already anticipates a report as one kind of pointer target, and `refreshedAt` is "refreshed by census on every run," a pointer rather than a copy of the data itself. `Profile.degenerateOutputConfidenceFloor` (ADR-070's tier-2 quality floor) has no `withXMeasurement` method wiring it to a `Measurement` at all — unlike `seedFolder`, which does (`withSeedFolderMeasurement`). ADR-070 shipped this floor unset specifically because "the score distribution over this corpus has never been measured," naming the exact gap this report closes.

**One thing this ADR does not need to solve**: `boilerplateDocumentFrequencyFloor` (ADR-074) already has its own re-analyzable data — `shingle_document_frequency` and `shingle_corpus_size` — sufficient on their own for an operator or stage 4 to act on. It needs no report of its own. That leaves `degenerateOutputConfidenceFloor` as the only currently-unset threshold this report exists to calibrate.

## Decision

**The report is a confidence-score distribution over `extraction_metric`'s `mean_score`/`low_score` columns, corpus-wide, computed once stage 2's run has fully finished.** Nothing broader: the other `extraction_metric` columns (size counters, garbage-text proxies, language) stay as ADR-073 left them — raw, re-analyzable data with no threshold reading them yet. A future threshold on any of those computes its own distribution when it exists, rather than stage 3 pre-computing summaries nothing consumes.

### Two outputs, not one

- **Re-analyzable data**: a new `extraction`-owned table (the distribution's home is the module owning the columns it summarizes) carrying the computed distribution — bucket boundaries and counts, or percentile values, keyed by stage 3's own `run_id`. This is census's own shape: measurement stored as data, not thrown away once read.
- **A single self-contained HTML file**, written to the working directory alongside `profile.yaml` and the database (ADR-054's placement rule — beside the database, never inside the corpus). No templating library: the pom carries what a recorded decision requires (ADR-046), and a confidence-score distribution — a table of buckets, an inline-SVG bar chart at most — costs little to assemble as a plain Java string and does not justify a new dependency. This is a per-corpus-run artifact generated by the pipeline itself at runtime, not a source-controlled doc — `docs/render-docs.mjs`'s Node-based generation is a different mechanism for a different kind of document (checked-into-git, edited by a person) and is not the precedent here.

### The Profile pointer names the file, not the table

`Profile.withDegenerateOutputConfidenceFloorMeasurement(Measurement)` is added, mirroring `withSeedFolderMeasurement`, called by stage 3 on every run. Its `Measurement.source` names the HTML file's path, not the raw table: `ProfileValue.measurement`'s own javadoc says the pointer exists to be "enough for a person to go and read the real thing," and a file path a person can open directly serves that better than a table name they would first have to know how to query. The raw table still exists for anything that wants to query it programmatically (a future automated calibration, say); it simply is not what the profile points at.

### Timing: only over a finished stage-2 run

Stage 3 mints its own run with the triggering stage-2 run as upstream, and only runs once that stage-2 run has finished. Stage 2's step can fail and resume mid-corpus via its circuit breaker (ADR-071); computing a distribution over a still-incomplete pass would silently shift on every resume, misleading whoever reads it into calibrating tier 2 against a partial corpus. This is the same completeness discipline ADR-054/ADR-055 already apply to walk resumability, read onto run resumability instead.

### Regenerated every run

Both outputs — the table row and the HTML file — are overwritten on every stage-3 run, not written once and left. `ProfileValue.measurement`'s `refreshedAt` is meant to reflect when the pointer was last true; a stale HTML file sitting behind a fresh timestamp would misrepresent what "refreshed" means.

## Consequences

**`Profile` gains a second `withXMeasurement` method**, closing the asymmetry ADR-070 left between `seedFolder` (wired to a `Measurement`) and `degenerateOutputConfidenceFloor` (not). The record on this pattern is now complete for both currently-defined thresholds — `boilerplateDocumentFrequencyFloor` needs no such method, since its own tables are its pointer target directly.

**A human has something to actually open.** Before this, an operator wanting to set ADR-070's tier-2 value had no path shorter than writing their own SQL against `extraction_metric`. After, `profile.yaml`'s `measurement.source` names a file that already shows the distribution.

**Module ownership**: the distribution table lives in `extraction` (the module owning the columns it summarizes), while writing it and generating the HTML requires reading `extraction`'s data and writing to `profile` — composition only `pipeline` may do, the same shape stage 2 used to compose `extraction` and `similarity` without either depending on the other. Stage 3's `implementationVersion` therefore spans `extraction`, `similarity` (ADR-074's boilerplate half), and `pipeline`'s own composition, under ADR-073's reading of ADR-058.

**Nothing here specifies the HTML's literal layout, the distribution table's column names, or the bucket/percentile scheme.** Those are the hand-off spec's to write, the same deferral every stage-2 ADR made to its own spec.
