## Decision

### 1. The output panel

**The output panel**, `output`, is a `TextArea`, not editable, wrapping no line, in the style class `output`, where the `ListView` stood. The operator selects any part of its text with the mouse or the keyboard and copies it with Ctrl+C or with Copy in its context menu, the `TextArea`'s own, whose Cut, Paste, Delete, Undo and Redo are disabled since it is not editable, and whose Select All stays. Nothing else copies it: there is no button.

**What it holds** is §7's: the watched invocation's whole output, as text, a line to a line.

**It follows new lines only while its view is at the bottom and nothing in it is selected.** Before each change of its text the window reads whether to follow: it follows where its view is at the bottom, its `scrollTop` within one line's height of its greatest, or it holds no text yet; and no text is selected, the selection's length being 0. A selection holds the view as a scroll up does: the operator scrolls back to the bottom and clears the selection, and from the next change on it follows again.

**How the text is added.** The window never sets the panel's whole text but where §7 replaces it once; otherwise it appends:

- following, it appends the new lines with `appendText`, puts the caret at the end and sets `scrollTop` to `Double.MAX_VALUE`, so the view stands at the new end;
- not following, it reads the selection's anchor and caret and the `scrollTop` first, appends with `appendText`, gives back the selection with `selectRange(anchor, caret)`, then calls the panel's `applyCss()` and `layout()`, in which the skin makes its own scroll to the caret, and only then sets the `scrollTop` it read, so neither the view nor the selection moves, whether the selection is in view or scrolled out of it.

### 2. The output file

**Each invocation that writes the invocation report (ADR-362 §3) writes `logs/output-<invocation.id>.log`** in its working directory, the id ADR-362 §3 mints and §4's copy is named by, beside it and beside `vespera.log`. The folder is made where it is not there, as ADR-362 §4 makes it.

**What it holds is what the invocation writes to its standard output and standard error through logback**, in the order logged, in UTF-8, a line flushed to the file as it is written, so a process killed by Stop leaves every line it logged before the kill:

- every line `CONSOLE` writes, in the console's pattern;
- every line `CONSOLE_WARN` writes, at WARN and above, in the console's pattern, so `com.zaxxer.hikari`'s and `TaskExecutorJobLauncher`'s lines below WARN are no more in it than on the console;
- every line of the jar's own (§4), as its words alone, whichever stream the console writes it to.

`vespera.log` is unchanged in its place, its rolling and its pattern, and keeps every line, the banner and the jar's own lines now among them (§4, §5, ADR-270). The output file is never rolled and has no cap: it is one invocation's, deleted by §6 alone.

**One sink, three appenders.** `InvocationOutput`, a class of `pipeline`, is the file's one sink, one to a logger context, held in it as an object under a name of its own, so that every appender of the context writes to the one file and a line is written whole before the next, whatever thread logs it. `InvocationOutputAppender`, a logback `UnsynchronizedAppenderBase` of `pipeline` with an encoder and the filters `logback-spring.xml` gives it, takes no lock of its own: it encodes an event and hands the bytes to the sink, **whose lock is the only one on the way to the file**. `logback-spring.xml` declares three: `OUTPUT`, in the console's pattern, which the root writes to beside `CONSOLE` and `FILE`; `OUTPUT_WARN`, in the console's pattern with a `ThresholdFilter` at WARN, which the two loggers of ADR-281 §1 write to beside `CONSOLE_WARN` and `FILE`; and `OUTPUT_OPERATOR`, `%msg%n`, which §4's logger writes to. Each names `<folder>${workingDir}/logs</folder>`, the folder `FILE` writes in, and `UTF-8`.

**Before the invocation begins** the sink holds what it is handed, in memory, in order: the banner (§5), Spring's start-up lines and anything logged before the lock. At §3's `begin` it writes what it holds into the new file, first, and from then on writes each line as it comes. It holds 4 MiB at most; where more would be held it drops the oldest lines whole, and at the `begin` writes first one line of the jar's own, `<n> lines logged before this invocation began are not in this file; logs/vespera.log holds them`. An invocation that never begins, refused before the lock or by picocli, or a `ProfileShapeCheck` refusal, writes no output file: what was held is dropped as the context stops.

**No warning is logged while the sink's lock is held.** A warning the sink has to give, of §2, §3 or §6, is kept while it holds its lock and logged on `InvocationOutput`'s logger once it has let the lock go, so that a thread logging, which takes the sink's lock to write, and the sink, which would otherwise log while holding it, never wait on each other. A warning so logged reaches the sink like any line.

**A file that cannot be opened fails nothing**, as ADR-362 §3 has a report that cannot be written: one warning, `the output file could not be opened: <exception class name>`, what was held dropped, and every line after it dropped without another warning. The invocation goes on, its console and `vespera.log` as they are.

**A write that fails once the file is open fails nothing either**: one warning, `the output file could not be written: <exception class name>`, the file left as it stands, neither truncated nor deleted, and every line after it dropped without another warning, the warning itself among them. The window then shows the file as far as it was written, and it grows no more (§7); the console and `vespera.log` keep every line.

### 3. How the appender learns the invocation

**The class that mints `invocation.id`, ADR-362's `InvocationReport`, begins the output with it before the report's first write**, so that a report naming an id is never written before the output file of that id exists, or has been tried. `InvocationReport` is given its beginning as a seam, `InvocationOutput.Beginning`, a functional interface taking the id, through its constructor:

- **as shipped**, `InvocationOutput::beginInThisContext`, which finds the sink of the logger context SLF4J is bound to and calls its `begin(String invocation)`, and **does nothing where that context holds no sink**: a test JVM, whose `logback-test.xml` declares none, and `vespera serve`, which Spring never configures;
- **in a test**, a recording `Beginning` of the test's own, given to the `InvocationReport` it builds, so that no test begins the shared test logger context and no `begin` of one test class meets another's.

A sink's `begin` is called once; a second call on the same sink is refused with an `IllegalStateException`, which only the sink of a jar's own context can meet. Nothing else names the id to logback: no system property, no MDC key and no property of the context, each of which a line logged before the id, or on another thread, would miss.

### 4. The jar's own lines go through logback

**Every line the jar prints outside logback today goes through logback, on the logger `io.algernon.vespera.operator`**, whose name `OperatorLines.LOGGER_NAME`, a class of `pipeline`, holds, declared with `level="INFO"` and `additivity="false"`, so that no level set on `io.algernon.vespera` or the root changes it. A line printed on standard output today is logged at INFO; one printed on standard error, at WARN. **Each reads as it does today**, its words alone with a line's end, on the stream it was printed on:

- `OPERATOR`, a console appender on standard output, `%msg%n`, its encoder's charset `${stdout.encoding}`, taking INFO and below and denying WARN and above;
- `OPERATOR_WARN`, a console appender whose target is `System.err`, `%msg%n`, its encoder's charset `${stderr.encoding}`, with a `ThresholdFilter` at WARN;
- `FILE`, in its own pattern, as it takes every line (ADR-270);
- `OUTPUT_OPERATOR` (§2).

The charsets keep the bytes of a line on a console that is not UTF-8 what `println` wrote; the control panel's child is started with both encodings UTF-8 (ADR-278 §1), so its stream is UTF-8 throughout.

**Which lines.**

- `VesperaCommand`'s 27 and the two refusals' are logged through the operator logger at the same place and with the same words.
- `publish`'s destinations are handed the operator logger's `info` where they were handed `System.out::println`.
- The usage of bare `vespera` is written with `CommandLine.usage(OperatorLines.out())`, so it is logged a line at a time and ends on no blank line.
- Picocli's own refusals are written through it too: `VesperaCommand.commandLine()` sets the `CommandLine`'s `setOut` and `setErr` to `OperatorLines.out()` and `OperatorLines.err()`, `PrintWriter`s that log each whole line written to them, the first at INFO and the second at WARN, a line's end not part of what is logged.
- **Every closing line, and ADR-362 §7's two report lines, go on the operator logger, as their words alone**: each line the Context lists, `run`'s line naming the next value and the failure and stop lines of stages 1, 2, 4a and 5a, of embedding scoring and of generation and of `StepFailureClosingLine`; `label`'s and `publish`'s, printed today; and `Report: <path>` and the report line. A closing line a later change adds is logged there too, by the Context's rule. Each keeps the level it is logged or printed at today, the report lines INFO, so a closing line logged today at ERROR is on standard error, which the window and ADR-281 §2 read with standard output as one stream. So the rule ADR-362 §7 and §8 give a reader, the closing line is the last line that does not start `Report: `, is read on the stream itself, where neither line carries the console's time, level, thread or logger.
- **The closing line stays the last line** (ADR-158, ADR-278 §5), **by an `afterStep` listener, as ADR-289 has it for a step that failed with an exception.** The six closing lines the Context finds inside a tasklet are no longer logged there: the tasklet records each, its words whole as today, with `RecordedClosingLines.record(StepExecution, String)`, and `RecordedClosingLines`, a `StepExecutionListener` of `pipeline`, logs in its `afterStep` every line recorded for that step execution, in the order recorded, on the operator logger at ERROR, and removes them.
  - **Where the lines are held.** In memory, in a `ConcurrentHashMap` `RecordedClosingLines` itself owns, keyed by the `StepExecution`'s id, each entry a list in the order recorded; never in the step's `ExecutionContext`, which `TaskletStep` puts back as it was where a commit fails after the tasklet returned (its `afterCompletion`, calling `copy`), so that a line recorded there would be lost. No transaction touches the map: a line recorded stays recorded, whatever becomes of the step's commit.
  - **How a tasklet reaches it.** One `RecordedClosingLines` is a bean of `pipeline`; `TaskletSteps` is given it as it is given its other collaborators, and registers it on every step it builds; `ByteLevelReductionTasklet`, `EmbeddingScoringTasklet` and `GenerationTasklet` are each given the same one as a constructor argument. `ByteLevelReductionTasklet` keeps its present constructor beside the new one, and the new one, taking `RecordedClosingLines`, carries `@Autowired`, so that Spring, finding two constructors, injects the shared bean through it rather than looking for a default constructor, which would fail the context's start: the present one makes a `RecordedClosingLines` of its own, so that the tests that build it with `new` and never read stage 1's line compile and run unchanged, and only a test that reads that line passes the holder it reads. `EmbeddingScoringTasklet` and `GenerationTasklet`, which no test builds with `new`, have the new constructor alone.
  - **Its order.** Being an `afterStep`, its lines come after `AbstractStep`'s `executed in` line and after its ERROR and stack trace, which no level set on a logger could put before them. `TaskletSteps` registers it after `StepFailureClosingLine`, so that, Spring Batch running `afterStep` in reverse order of registration, it runs first and `StepFailureClosingLine`'s line, where there is one, stays last, as today. **Neither implements `Ordered` nor carries `@Order`**, since Spring Batch sorts listeners that do before it reverses them, which would undo that order.
  - **Stage 1** records its line in its catch of an archive gone and then rethrows, as today; `StepFailureClosingLine` still says nothing for an archive gone (`StepFailure.archiveGone`).
  - **Five in a row**: `GenerationTasklet` records the line before it draws the tree, so that it is logged whatever the drawing does. A refusal of the deliverable root the drawing comes to is recorded after it, and is logged after it, last: the refusal is the line the operator acts on first, since no repair pass draws a tree until another root is named. A drawing that throws leaves the five-in-a-row line logged by `RecordedClosingLines`, and `StepFailureClosingLine`'s line for the exception after it, last.
  - **Repeated faults**: `The generation step finished under …` is logged by the tasklet, its clause on the tree empty, and the refusal of the deliverable root, recorded, is logged after it by the listener.
  - The words of every line stay; only the place each is logged from, and so its order against Spring Batch's lines, changes.

**What stays outside logback is `EntryPoint`'s, before Spring starts**: its two lines where the window cannot open, and `vespera serve`, which `EntryPoint.main` now hands on itself, before `VesperaApplication.main`, where `serve` is the first argument it passes on, giving `ServeCommand` `System.out` and `System.err` through its constructor that takes them, made public; `ServeCommand`'s constructor naming the two streams goes, and so does `VesperaApplication.main`'s hand-off of `serve`. A start with `serve` first that reaches Spring anyway, `VesperaApplication.main` called directly, is answered by `VesperaCommand.Serve.call`'s line on the operator logger at WARN, exit 1.

**The test of it**: no class of the jar but `EntryPoint` reads the field `System.out`, `System.err`, `FileDescriptor.out` or `FileDescriptor.err`, and none calls `Throwable.printStackTrace()` with no argument, which prints on standard error.

**The test configuration routes the logger as the jar does**: `logback-test.xml` declares `OPERATOR` and `OPERATOR_WARN` as above and the logger writing to them, so that a test that reads a line on `System.out` or `System.err` reads its words as it did.

### 5. The banner is logged

`application.yaml` sets `spring.main.banner-mode: log`. Spring logs the banner at INFO on the logger of `org.springframework.boot.SpringApplication`, so it is in the stream in the console's pattern, in the output file (§2) and in `vespera.log`. The banner's text is Spring's own; no `banner.txt` is added.

### 6. Fourteen days

**At `begin`, before it opens its own file, `InvocationOutput` deletes each output file more than 14 days older than the invocation**: a regular file directly in `<working directory>/logs` whose name is `output-<id>.log`, `<id>` reading as §3's id with or without its suffix, and whose id's instant is more than 14 × 24 hours before the instant of the id being begun. A file of exactly 14 days is kept. The age is read from the name, never from the file's times, which a copy or a touch changes, as `vespera.log`'s rolled files are aged by the date in their names. `InvocationOutput.isOutputFileName` is the one parse of such a name, which §7 uses too. Nothing else is deleted: a name that does not read as an output file's, a folder, the report's copies (ADR-362 §4 never deletes one), `vespera.log` and its rolled files, and anything outside `logs`. A file that cannot be deleted costs one warning, naming it and the exception's class name, logged after the sink's lock is let go (§2), and the next file is tried; the invocation goes on. **The sink is given its deletion**, `Files::delete` as shipped, so that a test gives one that refuses a file it names.

Only an invocation that begins deletes, in its own working directory, under the lock it holds; `serve`, a start refused before the lock and the control panel delete nothing.

### 7. What the window reads

**The window keeps reading its child's stream**, standard error merged in, with the one thread of ADR-278 §3. **`Child` keeps two things of it, in memory alone**:

- **the tail**, the last `TAIL_LINES`, 200, lines, for ADR-362 §8's fall-back on how a child ended alone: its last line that is not blank and does not start `Report: `; nothing shows the tail;
- **the held lines**, every line read from the start, in order, until the window lets them go, at most `HELD_LINES`, 10,000, the oldest dropped past it, with a **running count** of every line read since the start: `held()` gives a `Held(long count, List<String> lines)`, the last of `lines` being line `count`, and `letGo()` empties them and holds no line read after it.

**Which file is the watched invocation's.** The report ADR-362 §8 accepts as the watched invocation's, its `invocation.pid` the child's or, for an invocation the window did not start, the holder line's, and its `invocation.started` no earlier than the instant the window took before starting the child or than the holder line's `started` less a second, names the file: `<working directory>/logs/output-<invocation.id>.log`, **built only from an id `InvocationOutput.isOutputFileName` reads as §3's form** (§6), so that an id holding anything else, a `..`, a separator or a drive among them, names no file and the panel stays on the held lines. The window finds the file of an invocation it did not start in the same way, and only so.

**What the panel shows.**

- While no accepted report names a file that is there, the panel shows the child's held lines. At each tick it appends only the lines after the last one it showed, by the running count: the lines numbered after it that `held()` still holds. Where lines it never showed have been dropped, the count having passed the last it showed by more than the lines held, it appends first one line of its own, `<n> lines are not shown here; the output file and logs/vespera.log hold them`, then the lines held. A line written before Spring, or a refusal before the lock, is so shown. For an invocation the window did not start it shows nothing.
- Once one is there, the panel's text is replaced, once, by the file's, and the child's held lines are let go. From then on, at each tick of the window's clock, the window reads the bytes the file has gained since its last read and appends the whole lines among them, decoded as UTF-8; a last line not yet ended waits for its end. A file that stops growing, as after §2's failed write, leaves the panel as it stands.
- A new child, or a foreign holder whose accepted report names another file, empties the panel; an invocation that has ended leaves its text in place until then.

### 8. Every text of the window that is not a control can be copied

**Every text the window shows outside a control is a `SelectableText`**, a sealed interface of the control panel permitting two final classes nested in it: `SelectableText.Line`, which extends `TextField`, for a text drawn on one line, and `SelectableText.Wrapping`, which extends `TextArea`, for one that wraps; `SelectableText.line(String)` and `SelectableText.wrapping(String)` make them. The `Line` or the `Wrapping` is itself the node in the window, so it carries the id the label had, and a test looks it up as a `TextInputControl` and holds it a `SelectableText`. Each is not editable, not reached by the Tab key, in the style class `selectable-text`, which the stylesheet draws as the label it replaces, with no border and no background, its font, colour and padding the label's. Its text is selected and copied as §1's panel's is, with the same context menu. It keeps the id, the style classes and the wrapping the label had.

**How it gets its size from its text.** A `SelectableText` measures its text with a `javafx.scene.text.Text` of its own font, never shown, again whenever its text, its font or its width changes:

- **one line**: its preferred width is that `Text`'s layout width plus the padding and the skin's insets, and its preferred height one line's. **Its minimum width is the one a `Label` of the same text and style would have**, its padding and the width of the ellipsis, so that where space is tight it shrinks to the width the label would shrink to and the layout is as it was. Shrunk, it shows its text from the start, cut at its edge where the label's ellipsis would stand, with no ellipsis drawn; the whole text is still selected, by dragging or Select All, and copied. Since a `TextField`'s skin keeps the caret in view, which after Select All would leave the end of the text shown, **a `Line` puts its caret back at 0, its selection cleared, whenever its text changes and whenever it loses the focus**, so that a shrunk `Line` shows the start of its text again once the operator has copied from it;
- **wrapping**: its width is what its parent gives it, and its preferred height is that `Text`'s layout height wrapped at that width less the padding and insets, plus them; its `TextArea` shows no scroll bar.

**A wheel over it scrolls what holds it.** The `TextArea` of a wrapping `SelectableText` holds a `ScrollPane` that would take a wheel's turn even with nothing to scroll; a `SelectableText` filters each `ScrollEvent`, consumes it and fires a copy at its parent, so a wheel over a hint or a description scrolls the tab, the sidebar or the pane it lies in, as over a `Label`.

**Which texts.** The header's `where` and `child`; `outcome`; each step's stage, name, state and cost; every heading, status, starting line and hint of a launch field and of a preset; the converter's two image names; the preflight lines; the code sets listed; the command lines; a report not written yet; each profile row's title, key, description, value in use, cost, and the heading and hint of its provenance's field; the profile's problem and its lines; the Inclusions tab's and the folders not relevant's sentences; and every outcome line of a Save, an Add or a Repair. **A text the window draws in a later build is held to the same rule**, those of ADR-362's Report tab (§8 of that record) and native views (its §10) among them: whichever of the two builds lands second applies it to the other's texts, and ADR-362's owed tests that read such a text read it as a `TextInputControl` wherever this record's step 5 lands first.

**The tables of ADR-362's native views copy their rows.** Each `TableView` of an analysis report's view (ADR-362 §10's `table-<name>-<id>`) selects its rows, one or many, with the mouse and the keyboard as a `TableView` does, its selection model's mode `MULTIPLE`. Ctrl+C, or Copy in the context menu the table carries, puts on the system clipboard the rows selected, in the table's order, as lines of tab-separated text, one line to a row, each cell's text as the view draws it, a cell that leads somewhere, an `analysisReport` or a `path` cell, copying its link's text, its columns in the table's order, with no header line; a tab or a line's end inside a cell is written as one space, so that a row stays one line. Copy is disabled where no row is selected. **It lands in ADR-362's step 6 alone**, which builds the native view's table, whatever this record's steps have landed.

**What stays as it is**, the text of a control: a tab's title; a button's, a check box's, a radio button's and a link's text; the title of a sidebar section; a leg's summary, its name, bar and state, drawn in its `TitledPane`'s header, which folds it (ADR-361 §3); the percent drawn on a bar, centred on it (ADR-370 §1), which is the bar's own reading; the rows of a list or a tree, which the operator selects as rows; a chart's title, axes, ticks and legend, which the chart draws. **A tooltip's text is outside the rule**: it is help, shown while the pointer rests, and only visible text is covered. **A dialog's sentence is outside it too**: a dialog is a window of its own, which this record does not change.

**What "outside a control" is, as the test reads it.** From the window's root, the walk descends into every `Parent` that is neither a `Control` nor a `Chart`, and, of the controls, into a `ScrollPane`'s content, a `SplitPane`'s items, each `Tab`'s content, an `Accordion`'s panes and a `TitledPane`'s content, never its header; no other control is entered. A `Label` the walk reaches with a text that is not blank is a text the rule has missed.

## Consequences

- **The operator copies any part of the output, or all of it with Select All**, from the start of the invocation, the banner and the lines before the lock included, where the window showed the last 200 lines and copied none.
- **The same lines are in three places**: the stream, the invocation's output file and `vespera.log`, which keeps them with dates and every library line at INFO. The output file is the one a person or a script reads for one invocation alone.
- **A refusal and the jar's other printed lines read as they did**, on the stream they were printed on, now in the output file and in `vespera.log` as well.
- **A table of a native view copies its rows**, the rows selected as tab-separated lines that a spreadsheet or a text editor takes as they are.
- **`vespera.log` gains the banner and the jar's own lines**, in its own pattern, its place and rolling as they are, so it holds every line the stream does but the JVM's own.
- **A closing line that was logged reads as its words alone**, as the operator decided: `run`'s line naming the next value, the failure and stop lines of stages 1, 2, 4a and 5a, of embedding scoring and of generation, and the line of a step that failed with an exception lose the time, level, thread and logger before them on the stream, and each logged at ERROR, all but `run`'s, is on standard error.
- **`logs` grows by one output file per invocation that writes the report**, the size of its output; each is deleted by the first invocation that begins more than 14 days after it, in the same working directory.
- **A start of the jar now logs its banner**: in the stream its first line carries the console's time, level, thread and logger, and its other lines follow as Spring writes them.
- **Every read-only text of the window can be selected**, so the operator can copy a path, a refusal, a command line or a value in use, and the window looks and scrolls as it did.

## Known limits

- **A `TextArea` holds its whole text and lays all of it out.** The output of a long run, a line per occurrence per stage at INFO (ADR-093), can reach hundreds of thousands of lines and tens of megabytes; how the panel behaves at that size is not measured here. A size at which the panel does not hold is ground for a later record; the virtualised control stays refused until one (Alternatives refused).
- **What is written to the standard streams outside logback is in the stream and in neither file**: what the JVM or native code writes itself, what a library prints with its own `System.out` or `System.err`, and the stack trace the JVM's default handler prints for an exception nothing caught. The test of §4 sees the jar's classes alone.
- **A failed write of the progress page or of the invocation account is warned of after the closing line**: `ProgressPage`'s warnings (442, 496, 615) and `InvocationAccount`'s (329) are logged in `afterJob`, which follows every step's `afterStep`, so the WARN stands after the closing line until ADR-362's step 11 retires both writers.
- **Two threads' lines logged within one another's write** can stand in one order in the stream and in another in the file, since the console's appenders and the sink each take their own lock.
- **The replacement of the stream's lines by the file's** drops a selection the operator made in the first, and scrolls the panel to the end where it follows.
- **An invocation started by a jar built before step 3** writes no output file, so the panel shows nothing for it where the window did not start it, and the held lines where it did.
- **An output file is deleted only by a later invocation** that begins in the same working directory; a working directory no invocation begins in again keeps its files.
- **A line logged before the invocation began, past the 4 MiB held,** is in `vespera.log` and the stream alone; a line the window's held lines dropped before it was shown is in the output file and `vespera.log`.

## Alternatives refused

- **A `SiftingAppender` keyed by an MDC value.** The MDC is a thread's: a line logged on another thread, or before the id, would land in no file or in a default one.
- **The id set as a system property, or a property of the logger context, before Spring starts, and a plain `FileAppender` naming it.** The id is minted once the lock is held (ADR-362 §3), and an id minted earlier would name an invocation the lock refuses, whose report it never writes.
- **`begin` reaching the sink through the logger context alone, in tests as in the jar.** The test JVM shares one context across its classes, so a test's `begin` would meet another's.
- **The window writing the stream to the file.** The window writes nothing of what it reads (ADR-278 §3), and an invocation it did not start would have no file.
- **The output files rolled, or aged by their last-modified time.** One file is one invocation's, and a copy or a touch changes a file's time where its name keeps its start.
- **The `ListView` kept, with a copy of the selected rows or a button that copies all.** The operator wanted any part selected, not rows, and no button.
- **`jfx.incubator.richtext`'s `RichTextArea`**, virtualised, for the panel. It is an incubating module the pom does not carry, and a dependency wants a record of its own (ADR-046).
- **A `Label` given a context menu with Copy.** It copies the whole text and selects none of it.
- **The 200-line tail kept as what the panel shows.** The operator wanted the whole output.
- **The jar's own lines in UTF-8 on every console.** Their bytes on a console that is not UTF-8 would change; their charsets are the streams' own.
- **The jar's own lines kept out of `vespera.log`.** It keeps every line an invocation logs (ADR-270, ADR-281's Alternatives refused).
