# Generated code documentation: the marks a documentation generator writes into its pages

Research record for the decision in [What a code file is, and which stages it goes through](https://github.com/algernon28/vespera/issues/558) (map [#551](https://github.com/algernon28/vespera/issues/551)): which pages of generated code documentation stage 1 can recognise as code by their content. The generators are the 21 of Wikipedia's [Comparison of documentation generators](https://en.wikipedia.org/wiki/Comparison_of_documentation_generators), the list the operator named. Every claim comes from a public primary source, the generator's own templates or its published output, listed under Sources; no document of the operator's was read. Section 6 is a non-binding recommendation.

**Decided on 2026-10-18 (operator).** Only reference pages are code, so a dual-purpose generator needs its page-type check and its guides stay documents. The set is section 6's, with Sphinx left out until a density floor is measured. The list is built into the code and changed by a PR with an ADR. Marks are looked for in the files the name rule reads (PLAIN_TEXT, and UNRECOGNISED files that read as text), in their first and last 64 KB, and the HTML test is unchanged.

**Scope:** this covers the 21 generators in the "General information" table of Wikipedia's *Comparison of documentation generators*: Doxygen, fpdoc, Haddock, HeaderDoc, Imagix 4D, Javadoc, JSDoc, mkd, MkDocs, Natural Docs, NDoc, pdoc, perldoc, phpDocumentor, pydoc, RDoc, ROBODoc, Sandcastle, Sphinx, Visual Expert and YARD. **All 21 are covered; none is missing.** It also covers five that are not on that list: mkdocs-material/Zensical, mkdocstrings, pdoc3, pod2html and DocFX. For perldoc there are two entries (pod2html and perldoc/Pod::Simple), and phpDocumentor has entries for 1.x, 2.x and 3.x.

Windows used below: **P** = the 512-byte prefix, **F** = the first 64 KB, **L** = the last 64 KB.

## 2. Dual-purpose generators: telling an API page from a prose page

- **Sphinx.**
  - **API (3.x+):** `<dl class="py `, `<dl class="c `, `<dl class="cpp ` or `<dl class="js `. From 4.0 also `<dt class="sig sig-object py` (and c, cpp, js).
  - **API (≤2.x):** `<dl class="class">`, `"function"`, `"method"`, `"attribute"`, `"exception"` or `"data"`, plus `<code class="descname">` (1.3–3.x) or `<tt class="descname">` (≤1.2).
  - **Not API:** the `std` domain (`std option`, `std confval`, `rst directive`).
  - **Extras:** `<span class="viewcode-link">`, `<table class="autosummary`. Viewcode source pages start `<h1>Source code for `.
  - **Reliability:** high for domain-tagged objects. Two limits:
    - Hand-written reference such as docs.python.org/library has the same markup as autodoc output, so content cannot tell "generated from code".
    - One directive on a prose page flips that page. A density threshold would help; none was calibrated.
- **Doxygen.**
  - **API:** `class="memitem"` or `<table class="memberdecls">`.
  - **Prose:** `<div class="textblock">` with no memitem; from 1.8.20 the page also ends `</div><!-- PageDoc -->`. Verified: doxygen.nl markdown.html has 0 memitem and PageDoc; the LLVM class page has memitem from 3235 to 444520.
  - **Source listings:** `*_source.html` have `<div class="fragment">` and no memitem; they are code.
  - **Reliability:** high.
- **MkDocs, Material, Zensical.** A page is API only if it has mkdocstrings classes (`class="doc doc-object`). The head `_mkdocstrings.css` marks the site, not the page. Reliability: high.
- **JSDoc (default template).**
  - **Prose:** `<title>JSDoc: Home</title>` and `<title>JSDoc: Tutorial: `.
  - **API:** `Class: `, `Module: `, `Namespace: `, `Mixin: `, `External: `, `Interface: ` and `JSDoc: Global`.
  - **Code listing:** `JSDoc: Source: `.
  - **Themes:** use `class="container-overview"` or `<h4 class="name" id=`.
  - **Reliability:** high.
- **Natural Docs 2.x.**
  - **Prose:** topic classes containing ` LTextFile` (e.g. `CTopic TSection LTextFile`).
  - **API:** `CTopic T<Type> L<Lang>` plus `NDPrototype`.
  - 1.x was not checked. Reliability: medium.
- **YARD.**
  - **Prose:** `<div id='filecontents'>` (single quotes), a title starting `File: `, or a `file.*.html` name.
  - **API:** `<div class="box_info">`, `class="method_details`, or a title starting `Class: ` or `Module: `.
  - **Reliability:** high.
- **RDoc.**
  - **Darkfish:** `<body id="top" role="document" class="class">` or `class="module"` is API; `class="file"` is prose.
  - **Aliki:** `class="class has-toc"` is API; `class="file has-toc"` is prose.
  - **1.x:** `id="classHeader"` is API; `id="fileHeader"` is prose.
  - **Reliability:** high.
- **Sandcastle / SHFB.**
  - **API:** the Help.Id or Microsoft.Help.Id content matches `^(R|N|T|M|P|F|E|Overload|AllMembers\.T|Methods\.T|Properties\.T|Events\.T|Fields\.T|Operators\.T):`.
  - **Prose:** a GUID id means a conceptual page. `<meta name="container"` appears on API pages only.
  - Do not use `Microsoft.Help.ContentType`: several MAML conceptual types also map to "Reference".
  - **Reliability:** high.
- **DocFX.**
  - **Modern template:** `data-yaml-mime="ManagedReference"` or `"ApiPage"` is API; `data-yaml-mime=""` is prose.
  - **Default template:** a non-empty `data-uid` plus `<div class="inheritance">` or `_syntax">Syntax</h5>` is API.
  - **Reliability:** medium.
- **phpDocumentor 3.**
  - **API:** `<article class="phpdocumentor-element -class` (also `-interface`, `-trait`, `-enum`) and `phpdocumentor-signature`.
  - **Guides:** `<section class="section" id=` with no `phpdocumentor-element`.
  - **Reliability:** high.
- **phpDocumentor 1.**
  - **API:** `<h2 class="class-name">` and `<div class="method-signature">`.
  - **Prose:** `tutorial_*.html` pages, which lack both.
  - **Reliability:** high.
- **Javadoc (mostly API).**
  - **Not API (17+):** generator `javadoc/DocFileWriter` or `javadoc/HelpWriter`, body `doc-file-page` or `help-page`.
  - On ≤16, doc-files are copied verbatim and carry no markers.
- **pod2html / perldoc.** There is no reliable way to tell them apart: POD prose and module docs render the same. A weak heuristic is a NAME line like `Foo::Bar - ` plus `use Foo::Bar` in the SYNOPSIS. Reliability: low.
- **fpdoc.** Topic pages lack `<h2>Declaration</h2>` and `Source position: `. Reliability: medium.

## 3. Which reading window suffices

- **The 512-byte prefix (P) is enough for:**
  - Javadoc (all versions), pdoc, pdoc3, Imagix 4D, JsDoc Toolkit, pydoc, NDoc head, DocFX ≤2.59.
  - The JSDoc title.
  - Doxygen 1.8.3+ meta. With a custom header that dropped the meta, the comment is in F instead.
  - HeaderDoc 8.9.
  - Natural Docs 2.3+ html class.
  - The YARD title, if not overridden.
  - The phpDocumentor 1 frames comment.
  - Material, mostly. Zensical puts its meta at up to 1.5 KB, which needs F.
- **The first 64 KB (F) is needed for:**
  - Comments past the prefix: Doxygen (1–3.5 KB), ROBODoc (400–550), Natural Docs (both lines).
  - HeaderDoc 8.0 meta; Sandcastle Help metas (0.7–2.2 KB); DocFX modern `data-yaml-mime`.
  - Class or structural markers: phpDocumentor 3 classes, fpdoc structure, Visual Expert structure.
  - The Pod::Simple::HTML comment, the pdoc attribution, the recent RDoc footer.
  - The Sphinx head (except Furo).
- **The last 64 KB (L) is needed for:**
  - **Haddock** (its only marker).
  - **YARD**, when `--title` is set.
  - Footers: MkDocs core, Material/Zensical, Sphinx, JSDoc, phpDocumentor 1 and 2, RDoc 4.x and Aliki, NDoc, Imagix, Doxygen, DocFX, pdoc3, HeaderDoc.
- **Page-type markup** can need L on big pages with large navigation. On Material/Zensical the first `doc doc-object` was at 105–155 KB, so F misses it and L catches it, because the API body runs to the footer. A page over 128 KB with API content only in the middle would be missed; that is rare.
- **Pages the content-based HTML test misses** (only the .html/.htm name catches them):
  - A UTF-8 BOM: Natural Docs 2.1+, SHFB, DocFX 2.56.
  - An `<?xml` prolog: pod2html (Perl 5.8+), RDoc 1.x and Darkfish 2–3, phpDocumentor 1 frames/HandS, ROBODoc 4.99, JsDoc Toolkit on some hosts.
  - A leading comment: Doxygen `<!-- HTML header for doxygen ` (Eigen, doxygen.nl).
  - Doxygen pages written with a `.php` or `.asp` extension.

## 4. Generators with no reliable marker, and what a rule would miss

- **No generator string at all:** pydoc, fpdoc html, phpDocumentor 3, pod2html, Pod::Simple::XHTML (writes nothing identifying), Sandcastle (Help metas only), and Visual Expert content pages (generic Gentelella admin theme). mkd writes no HTML.
- **Markers users can remove or override:**
  - Sphinx footer: `html_show_sphinx`.
  - YARD title: `--title`, common.
  - Material footer: `extra.generator`.
  - MkDocs: theme override.
  - RDoc: sdoc/hanna templates, common for Rails API docs.
  - JSDoc: third-party themes drop the title.
  - DocFX: `_appFooter`.
  - Doxygen: HTML_FOOTER, though the hard-coded comment remains.
  - ROBODoc: `--headless`.
- **A rule would miss:**
  - Javadoc from custom doclets (rare).
  - YARD/RDoc built with fully custom templates.
  - Doxygen pages with a custom header that need F rather than P.
  - CHM contents (compressed).
  - Generators outside the 21, such as rustdoc, TypeDoc, Dokka and Epydoc (not researched).

## 5. Non-HTML outputs: what stage 1 sees

- **CHM.**
  - Magic at byte 0: `ITSF` 03 00 00 00 60 00 00 00.
  - Producers: Doxygen, fpdoc (native), NDoc, SHFB, RDoc 1.x, phpDocumentor 1.x, Sphinx (htmlhelp builder + hhc) and Haddock 0.x (project files only).
  - The pages inside are LZX-compressed, so stage 1 sees the magic and nothing else.
  - Help manuals written by hand share the same magic, so **CHM must not be classed as code by magic alone**.
  - Help 2 `.HxS` files start `ITOLITLS`.
- **man.**
  - **Doxygen:** `.TH "<name>" 3 "<date>" ... \" -*- nroff -*-` (P), and `Generated automatically by Doxygen for <proj> from the source code.` at the end (L). This is the only API-specific man marker.
  - **Pod::Man:** `.\" Automatically generated by Pod::Man ` (P). Dual-purpose: perl prose pages carry it too.
  - **docutils/Sphinx:** `.\" Man page generated from reStructuredText` (P). Usually prose.
  - **ROBODoc:** a troff comment `Generated with ROBODoc Version`.
- **PDF.** Only `%PDF-`; the streams are compressed. Stage 1 cannot tell the generator.
- **RTF.**
  - Doxygen: `{\rtf1\ansi\ansicpg` with ` doxygen <ver>.}` in the info block (F).
  - ROBODoc: `{\rtf1\ansi \deff0` with `Generated with ROBODoc Version`.

## 6. Recommendation

**Rule shape:** a page is generated code documentation when it has a generator marker AND either the generator is API-only or a page-type marker says API. Match raw tags only: a prose page that quotes a marker escapes it as `&lt;meta`. Match case-insensitively, collapse whitespace (several footers are split across lines), and accept quoted or unquoted attributes (minified Material).

**Match on the marker alone (API-only generators):**
1. Javadoc: `<!-- Generated by javadoc` (P). Optionally exclude `content="javadoc/DocFileWriter"` and `"javadoc/HelpWriter"`.
2. pdoc and pdoc3: `<meta name="generator" content="pdoc` (P).
3. Haddock: `Produced by <a href="http://www.haskell.org/haddock/">Haddock</a>` (L).
4. HeaderDoc: `<meta name="generator" content="HeaderDoc"` (F).
5. ROBODoc: `<!-- Generated with ROBODoc Version` (F); fall back to `>ROBODoc</a> V` (L).
6. Imagix 4D: `created by Imagix 4D -->` (P).
7. NDoc: `<body id="bodyID" class="dtBODY">` (P). It also matches Microsoft MSDN SDK pages, which are API anyway.
8. mkdocstrings: `class="doc doc-object doc-` (F and L).
9. phpDocumentor 2: the http:// footer `Documentation is powered by <a href="http://www.phpdoc.org/">phpDocumentor`. The https form also appears in the 3.x clean template, which has guides, so it needs a page-type check.
10. pydoc: `<title>Python: ` plus one of the heading markers (P). Medium.

**Match the generator plus a page-type check (dual-purpose generators; section 2 gives the strings):**
- Doxygen: meta, or the regex `<!-- [^<>]{1,40} Doxygen \d[\d.]* -->`, plus memitem or memberdecls.
- Sphinx: domain-tagged `dl`/`dt` only, never `std`. No generator marker is needed.
- JSDoc, YARD, RDoc, Natural Docs, SHFB, DocFX, phpDocumentor 3 and phpDocumentor 1.

**Leave out:**
- **MkDocs core, Material, Zensical generator meta and footers.** These tools render prose only, so the marker would turn every guide into code.
- **Sphinx footer and head markers on their own.** They are on every prose page (checked on python tutorial/introduction).
- **pod2html and perldoc.** There is no API-versus-prose test, and `rev="made"` also appears in old hand-written HTML.
- **Visual Expert.** Only index.html names the tool, the content-page structure is a generic admin theme, and the tool is niche.
- **fpdoc.** Optional; it can only be matched by structure (`fpdoc.css` + `bartitle` + `Source position: `). Medium. Add it if Pascal archives are likely.
- **CHM and PDF by magic.** Prose manuals share the same magic.
- **Site-level strings** such as `documentation_options` and `_mkdocstrings.css`.

**Markers that misfire on prose guides:** every generator-identity marker of a dual-purpose tool does, so these need the page-type check:
- Doxygen comment and meta on `\page` and Markdown pages (verified on the doxygen.nl manual).
- The Sphinx footer.
- The Material meta.
- The JSDoc title on Home and Tutorial pages.
- YARD and RDoc footers on README pages.
- Natural Docs on `.txt` pages.
- SHFB and DocFX conceptual pages.
- phpDocumentor 3 guides.
- Javadoc doc-files on 17+.
- Sphinx `sig sig-object` without a domain on CLI and config pages.

**Prerequisite:** the HTML test should skip a UTF-8 BOM and accept an `<?xml …?>` prolog or a leading `<!-- … -->` before the doctype. Otherwise the pages listed at the end of section 3 reach the rule only through the .html/.htm name.
